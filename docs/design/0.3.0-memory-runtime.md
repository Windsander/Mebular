# Memory Runtime (0.3.0)

[中文](0.3.0-memory-runtime_CN.md) · [Documentation index](../README.md)

Mebular 0.3 moves memory from "a set of tools" to "a runtime". The same local daemon
can now recall, extract, compact and checkpoint memory for an assistant, while the
data stays in the graph, event log and sync layer you already have.

This is the user-facing guide. The implementation contract is
[`0.3.0-memory-runtime-contract.md`](0.3.0-memory-runtime-contract.md) (Chinese).

## Memory as runtime, not tools

In 0.2 the host model does the thinking. It calls `memory_write` when it decides
something is worth keeping, and `memory_query` when it wants it back. Mebular is a
memory service behind a tool surface.

In 0.3 the host can also hand Mebular a conversation slice, a task state or a set of
candidate records. The runtime then does the work:

```text
host conversation / task
  -> host adapter (MCP client, DSH plugin, Hermes provider, OpenCode plugin)
  -> /runtime/v1  ingest · recall · context · checkpoint
  -> RuntimeService
  -> existing graph + signed events + sync + cloud
```

This is still the same Mebular graph. The runtime does not create a second store,
a second sync protocol or a second daemon. It reuses the nodes, events, tombstones
and subscriptions that 0.2 already has.

What does **not** change:

- The 29 MCP tools (`memory_*`, `task_*`) keep their names, arguments and meaning.
  There are no `runtime_*` MCP tools.
- Existing nodes, events, namespaces, tags and history are not migrated or rewritten.
- MCP remains a first-class path. A host that only wants explicit tool calls never
  needs to touch the runtime API.
- The HTTP runtime runs inside the same `mebular serve` process and obeys the same
  single-writer lock. The stdio `mebular mcp` path does not carry `/runtime/v1`; a host
  that wants immersive processing connects to the daemon.

## Two access modes

Mode is a **device-local setting**. One device can use lightweight MCP while another
device in the same cloud uses the immersive runtime; the shared MemoryRecords are the
same.

| | Lightweight MCP (default) | Immersive Runtime (opt-in) |
|---|---|---|
| Who drives | The host model | The runtime, with the host adapter |
| What Mebular does | Provides memory tools | Extraction, recall, context assembly, compaction, checkpoints |
| Raw conversation | Not captured | Captured only when the device or the adapter requests `capture=local` |
| Model calls | None | Only the source you configure |
| 0.2 behavior | Unchanged | Not used until you switch |
| Write endpoints | `/runtime/v1` writes return `409 mode_mismatch` | Enabled |

### Lightweight MCP

This is the default and the compatibility path. The assistant decides what to write
and when to search. Mebular does not read the conversation, does not call a model and
does not create RawChunks, Compacts or Checkpoints unless an administrator explicitly
calls the runtime API.

Use it when you want memory to be an explicit tool, when you do not want a local model,
or when several assistants should share one graph with minimal surprise.

### Immersive Runtime

The host adapter sends the parts of the conversation or task it wants processed to
`/runtime/v1/ingest`. The runtime can:

- keep the original text locally as a RawChunk when capture is `local` (off by device
  default; an adapter may request it per ingest);
- extract MemoryRecords with rules, a local Qwen model, host-provided candidates or an
  OpenAI-compatible API;
- build `context` blocks for the next model call;
- fold a compaction into a `ContextCheckpoint`;
- write a `SelfRecord` for the agent.

The host can keep using MCP for explicit governance, search and task management.
Immersive is not "the runtime takes over every conversation": only what an adapter
sends is processed.

### Switching modes

Switching `mcp` ↔ `immersive`:

- applies to the current device only;
- does not migrate, copy, rewrite or delete any node;
- keeps every MemoryRecord, Compact, SelfRecord, cloud Checkpoint and local Raw/Trace
  where it was;
- stops new capture, extraction and checkpoint writes when switching back to `mcp`;
- keeps `status`, `recall`, `context`, checkpoint reads and self reads available.

A switch is not a data conversion. If you switch back, 0.2 behavior is what you get,
and the runtime objects remain in the graph but stay hidden from normal memory queries.

## Shared base and where each object lives

"Cloud" here means your Mebular cloud (忆云): the devices that share one user master
key. There is no central memory server; the existing event log and direct sync carry
the data.

| Object | Where it lives | Shared across devices | In normal memory queries | Purpose |
|---|---|---|---|---|
| **MemoryRecord** | Existing graph nodes (`entity` / `fact` / `episode` / `skill`) | Yes, by namespace subscription | Yes | Durable user memory: facts, preferences, episodes, skills |
| **Compact** | Graph node, same namespace as its sources | Yes, with that namespace | No | Derived summary with `sourceIds`; never replaces the source records |
| **SelfRecord** | Graph node (default cloud) or local file | Yes by default; logical `agentId` scope | No | One agent's long-lived self model, not a user profile |
| **ContextCheckpoint** | Local file by default; cloud graph only when `sync=cloud` | Only in cloud mode | No | Task/thread resume point with revision and lease |
| **RawChunk** | `<home>/runtime/` on this device | Never | No | Original captured text; not in the graph or event log |
| **RecallTrace** | `<home>/runtime/traces.jsonl` | Never | No | Local recall diagnostics and feedback |

The rules behind the table:

- **MemoryRecord is the only object that enters ordinary memory queries.** It uses the
  existing five node types and the existing edges.
- **Compact is derived and non-destructive.** It stores a summary and source IDs. If a
  source is deleted or changed, the compact is marked `stale` when read; it is not
  deleted automatically.
- **SelfRecord and Checkpoint are not user memory.** They are hidden from `query`,
  `search`, `history`, `profile`, `skills` and `graph` by default.
- **Raw and Trace never leave the device.** They are not in the graph, not in the event
  log, not in snapshots and not in sync.
- **No new event types or wire protocol.** Runtime nodes are normal nodes; old peers can
  store them and simply do not show them.

## Four model sources

The runtime never chooses a model behind your back. There are four sources:

| Source | What it is | Network | Default | Good for |
|---|---|---|---|---|
| **No model** (`heuristic`) | Built-in rule extraction | None | Yes | Always-available baseline; predictable and private |
| **Local Qwen** (`local`) | Curated Qwen pack running on this device | None after install | Off | Offline extraction and summaries with better quality |
| **Current chat model** (`host`) | The host submits structured `CandidateRecord`s | Decided by the host | Off | Reusing the model the user is already talking to |
| **Third-party API** (`api`) | One OpenAI-compatible endpoint | Yes, explicitly allowed | Off | Devices without local compute |

### No model: heuristic

Deterministic rules extract clear preferences, explicit facts, decisions and task
episodes, and expand recall keywords. It is always available, needs no download and
never sends data anywhere. It is the default for a reason: a new install should never
need a model to work.

### Local Qwen: curated packs

Mebular supports three explicit packs. Nothing is downloaded or updated silently;
you install a pack in Console **Settings → Runtime → Local models** and then select it.

| Pack | Tier | Quantization | Context | Approx. download | Minimum RAM | Recommended RAM |
|---|---|---|---|---|---|---|
| Qwen 9B | Default | Q4_K_M | 32k | ~6.3 GB | 16 GB | 24 GB |
| Qwen 27B | High quality | Q4_K_M | 32k | ~17.6 GB | 40 GB | 64 GB |
| Qwen 4B | Lightweight | Q4_K_M | 32k | ~2.9 GB | 8 GB | 12 GB |

The runtime starts `llama-server` on loopback, uses a random local token and talks to
its OpenAI-compatible endpoint. The model runs locally; prompts and memory text are
not uploaded. A pack that is not installed or fails its manifest/checksum check is not
used. If it fails at runtime, the result is marked degraded and falls back to
heuristic rules.

### Current chat model: only what the host naturally provides

Mebular does **not** read the host's credentials, discover the host's endpoint or call
the host model. The host must produce candidates and submit them:

- DSH: optional idle `maintenance` uses the current DSH session model.
- Hermes: the optional `mebular-companion` plugin uses `ctx.llm`.
- OpenCode/OpenChamber: the optional plugin uses `ctx.session.generate` after a turn.

If the host asks for `extractor=host` but supplies no candidates, the runtime does not
invent any and does not silently call another model. Direct API callers get
`202 pending`; the host can fill the candidates later or choose another source.

### Third-party API: explicit and device-local

The API source accepts a single OpenAI-compatible base URL, model name and key
reference. Remote use requires both `runtime.model.api.allowRemote=true` and a
request-level `allowRemote=true`. The key is stored as a reference:

- `env:MEBULAR_RUNTIME_MODEL_API_KEY`
- `keychain:mebular-runtime/<cloudId>` (macOS Keychain in 0.3)
- `file:secrets/runtime-model.key` (relative to the Mebular home, `0600`)

Plaintext keys are never written to `config.json`, graph metadata, events, logs, the
Console or `/runtime/v1/status`. URLs are normalized and reject non-HTTPS endpoints
(loopback HTTP is the exception), userinfo and cloud-metadata addresses. A timeout,
5xx or 429 falls back to heuristic rules; Mebular never switches to another provider
on its own.

### How the source is chosen

`runtime.model.source` is the configured source. The runtime reports both the
configured source and the **active** source in `/runtime/v1/status`. `auto` resolves in
this order:

1. host candidates supplied with this request;
2. an installed local pack;
3. an allowed API configuration;
4. heuristic.

A configured local pack that is broken falls back to heuristic, not to the API. A
model failure is visible as `degraded` with a reason and warnings; it is never silently
reported as success.

## Host boundaries

Each host keeps its own product surface. Mebular adds a memory path; it does not take
over the host's native memory.

| Host | Default path | Immersive path | Native memory | Current model |
|---|---|---|---|---|
| **DSH** | MCP (`mcp__mebular__*`) | Opt-in `memoryRuntime` bridge | Not touched | Optional idle `maintenance` with the DSH session model |
| **Hermes** | MCP | Opt-in `MemoryProvider` plugin | `MEMORY.md` / `USER.md` stay active; no import, no dual write | `MemoryProvider` has no model; optional `companion` uses `ctx.llm` |
| **OpenChamber / OpenCode** | MCP through OpenCode global config | Opt-in `@mebular/opencode-plugin` (OpenCode >= 2.2) | Read-only coexistence; never imported, replaced or written | Only when explicitly selected; `ctx.session.generate` after a turn |

### DSH

The DSH plugin remains attach-first. `memoryRuntime` is off by default, and when it is
off the plugin registers no listener, starts no timer and makes no runtime request.
When enabled, it handles recall, ingest and compaction checkpoints; `maintenance` can
use the current session model to submit host candidates. The memory tools can be
hidden from ordinary agents while `task_*` and a governance allowlist stay visible.
No new MCP tools are added.

See [DSH integration](../integrations/DSH.md).

### Hermes

Hermes allows one external `MemoryProvider`. Mebular's provider plugs into that slot,
but the built-in `MEMORY.md` / `USER.md` memory remains active. Mebular does not import
it, mirror it or dual-write it. The provider exposes no tools; MCP remains the explicit
governance surface. Because the `MemoryProvider` interface has no current-model field,
candidate extraction by the host model is a separate, optional companion that uses
`ctx.llm`.

See [Hermes integration](../integrations/HERMES.md).

### OpenChamber / OpenCode

OpenChamber reuses OpenCode's global config. Mebular only adds
`mcp.servers.mebular`; it never writes OpenChamber's private `opencode.managed.json`.
The immersive plugin is an explicit opt-in and only uses OpenCode's `context` hook and
session events. OpenChamber's native memory is detected read-only and is never imported,
replaced, written or exposed as a Mebular tool. Current-model extraction runs only when
the user selects `host`/`current`, and falls back to heuristic when `session.generate`
is unavailable.

See [OpenChamber integration](../integrations/OPENCHAMBER.md).

## Privacy, governance, deletion and failure

### Data boundaries

- **Raw stays local.** `runtime.capture` is `off` by device default. A host adapter may
  request `capture=local` for a specific ingest; the text still stays on this device.
  `local` stores RawChunks under `<home>/runtime/raw/` with `0600` files and `0700`
  directories, for 7 days by default. Raw is not in the graph, events, snapshots or sync.
- **Traces stay local.** Recall traces keep a redacted query preview, hit IDs and
  timings; they do not keep full text or model prompts. Default retention is 7 days or
  2,000 entries.
- **Model settings stay on the device.** Model source, pack path, API URL and key
  reference are device-local. They are not shared memory.
- **Records carry provenance, not secrets.** A shared record may say which extractor
  and model produced it, but another device cannot replay that model or use its key.
- **Prompt safety.** Recalled memory is inserted as untrusted background data, not as
  instructions. Model output is parsed as data, schema-checked and never executed.

### Governance and deletion

- Internal objects (`compact`, `context_checkpoint`, `self_record`, and defensively
  `raw_chunk` / `recall_trace`) are hidden from default queries, graph traversal and
  the Console memory list. Admin views can opt in with `includeInternal=1`.
- `memory_delete` and `memory_archive` refuse internal objects; runtime admin endpoints
  are the explicit path for those.
- Deleting a MemoryRecord writes a tombstone and syncs it. This is cooperative: a copy
  already held by an offline peer may survive until that peer reconnects. There is no
  "delete domain" operation.
- Deleting a RawChunk is immediate and local. Deleting a Checkpoint removes the local
  file or tombstones the cloud node. Deleting a Compact does not touch its sources.
- The 0.3 authorization model is still **one cloud, one user**. `agentId` is an
  assertion, not an authentication boundary; SelfRecord and Checkpoint filtering is
  logical, not cryptographic. `memory.read` is cloud-wide; namespace ACLs are not part
  of this release.

### Failure and fallback

| Situation | What happens |
|---|---|
| Local model not installed or fails | `model_unavailable`; heuristic fallback; `degraded=true` |
| API not allowed / not configured | No request is made; `remote_not_allowed` or `model_unavailable` |
| API timeout, 5xx or 429 | At most one retry, then heuristic; no provider switch |
| Host requested but supplied no candidates | `202 pending` on the API; no silent model substitution |
| Ingest extraction fails | Chunks stay available (local capture if enabled); extraction is marked failed and can be retried |
| Compact fails | Source records are untouched; no compact is created |
| Context assembly fails | Existing blocks and warnings are returned; a broken checkpoint is skipped |

Mebular does not call a model unless you configured a source and the host sent the
required data. Failures are reported in `status.degraded` and `warnings`; there is no
silent "best effort" that pretends memory was written.

## What 0.3 does not do

- No multi-user accounts or per-person ACL inside one cloud.
- No cryptographic isolation between agents. SelfRecord and Checkpoint are filtered by
  `agentId`, not encrypted per agent.
- No namespace-level ACL. `memory.read` still reads the whole cloud.
- No automatic capture of every conversation. Only explicit `/ingest` input is processed.
- No cloud Raw/Trace, no silent model download, no automatic model update.
- No model-configuration sync across devices.
- No destructive compaction and no automatic merge of conflicting facts.
- No cross-cloud merge or federation.
- No additional MCP tools. The tool surface stays at 29.

## Compatibility and rollback

- 0.2 clients keep their default `query`, `search`, `history`, `profile`, `skills` and
  `graph` results. Internal runtime objects are filtered defensively.
- 0.2 data is read as legacy data. No field is added, no ID is changed, no event is
  re-signed.
- Mixed versions can sync: old peers may store unknown runtime node types but will not
  show them in default queries.
- Rolling back to 0.2 keeps the graph intact. Runtime objects remain stored and hidden;
  local `runtime/` files are simply ignored by the older code. Keep the `runtime`
  config section when rolling back so a later upgrade can reuse it.
