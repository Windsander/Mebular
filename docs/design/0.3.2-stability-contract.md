> **Status:** Chief approved on 2026-11-04; binding implementation target for WP1–WP6. Not an implementation or acceptance report.
> **Date:** 2026-11-04
> **Baseline:** `beba4f35c7f001d6109f1bb02fdce1cb67dc3133` (`origin/main`, including documentation calibration PR #304).
> **Integration baseline:** `feat/0.3.2-stability` at the same SHA.
> **Chinese:** [v0.3.2 稳定性契约](0.3.2-stability-contract_CN.md).

This is the single behavioral target for v0.3.2 WP1–WP6. The English and Chinese files carry the same contract IDs; a wording difference is a documentation defect, not permission to implement different behavior. This document does not replace historical v0.3.0 reports or user guides.

## 0. How to read this contract

- **Baseline fact** describes the source, tests, or calibrated documentation at the baseline SHA. It is not a claim that the behavior is correct.
- **Target** is chief-approved required v0.3.2 behavior. It is not a claim that the behavior already exists or has passed tests.
- **Evidence** identifies tests that can decide pass/fail. Historical results do not become evidence for a new SHA.
- **Must/must not** are normative. All D1–D6 resolutions in §10 are final for v0.3.2; execution sessions have no alternative branch or local waiver to choose.

The following existing boundaries are invariant:

1. Keep the 29 public MCP tools and their existing semantics. Add no public `runtime_*` tool, host, model source, sync wire protocol, event type, second memory store, or cross-device consistency protocol.
2. The MCP daemon owns the graph, event log, sync, and capability API. The sidecar never writes the graph directly.
3. Lightweight MCP remains the default and starts no sidecar, collection, model download, or remote model call.
4. One cloud and one user remain the trust model. `agentId`, domain participation, and lease ownership are logical assertions, not authentication, namespace ACLs, or cryptographic agent isolation.
5. Local graph commit is not remote sync. Tombstone propagation is cooperative; no Mebular operation guarantees physical erasure on offline peers, in host-owned files, or in model-provider logs.
6. No large Console redesign or repository-wide rewrite is authorized. If a target cannot be implemented within these boundaries, stop and use chief change control rather than inventing a parallel contract.

### 2.3 Data minimization and evidence association

1. Redaction and minimization happen before staging, outbox, Hermes spool, logs/status, or remote-model requests. Persist only fields needed for extraction, idempotent replay, retention, and diagnosis.
2. A multi-domain extraction must select the actual supporting chunk/message IDs for each domain. Do not copy the whole request's unrelated chunks into every domain. If the same evidence genuinely supports two domains, create separate same-domain DetailRecords with their own IDs and references.
3. The canonical record↔detail association is the validated, same-domain `DetailRecord.recordIds` plus the existing reverse lookup. Do not add a post-settlement MemoryRecord rewrite merely to denormalize `provenance.detailIds`; baseline capability drops that forward field. If a legacy/provided forward field exists, it must agree and must not be advertised as the only lookup. `rawChunkIds` remains compatibility metadata, not a staging-ID substitute for a graph Detail ID.
4. Checkpoint `recordIds/detailIds` and `state.references` graph IDs must be validated for existence, expected type, live state, and same domain at capability commit; invalid queued references fail/dead rather than committing dangling evidence. External message IDs remain host references, not graph proof. No evidence means no invented link.
5. `tool` role or `detailKind=tool_output` selects `tool_output`; `document_slice` selects `document_slice`; ordinary user/assistant/system conversation uses `conversation`; `pinned` requires explicit governance. Runtime and core detail-kind enums must match the core/canonical set. Server policy may shorten but never silently extend retention. `retentionClass` applies to DetailRecord only, not Compact/Checkpoint/SelfRecord.
6. Authoritative Detail expiry does not delete MemoryRecord, Compact, Checkpoint, or SelfRecord. Local process cleanup never deletes graph objects. Detail governance deletion remains online-only in v0.3.2; no offline sidecar detail-delete producer is added.
7. **Graph deletion is not physical content erasure.** Baseline create/update events contain full node versions and tombstoned nodes retain content (`src/core/GraphStore.ts:60-73,100-111,162-192`). The same disclosure applies to synced snapshots, old Checkpoint/Self revisions, Compact history, outbox/dead bodies, and the capability idempotency ledger. v0.3.2 must test and document these copies rather than claiming secure/local erasure; changing that event/history format is outside scope.
8. Cleanup is dependency-aware. If an active outbox/pending operation still needs staging evidence, cleanup must first make that dependent operation visibly failed/dead at its earlier deadline, or complete its settlement; it must not delete staging and later commit a supposedly complete ingest with silently missing details. Partial object commits follow §3 and remain explicitly partial.

## 3. Persistence and failure state machine

### 3.1 Target vocabulary

| Term | Exact meaning | Must not mean |
|---|---|---|
| **accepted** | Authentication, mode, schema, and admission checks passed; processing has begun. It is an ingress observation, not a durable outcome. | Queued, graph committed, or remotely synced. |
| **pending** | Non-final work still needs extraction, a host candidate, a capability response, or conflict resolution. Any user-visible pending that survives a response must have a durable recovery record or a bounded transition to failed. | Committed, indefinitely retrying by default, or proof that a request reached MCP. |
| **queued** | A specific pending operation has been atomically persisted in sidecar outbox or a disclosed host spool with a stable idempotency key before the host receives acknowledgement. | Graph write succeeded. |
| **committed** | MCP capability returned success for every required write and the object(s) are present in the local graph/event log. `duplicate` counts only when it resolves the same idempotent logical object. | Merely staged, merely enqueued, process healthy, capability reachable, or synced to a peer. |
| **failed** | This attempt/operation reached a terminal, visible failure without automatic retry. | A successful or unknown commit may be relabelled as definitely absent after an ambiguous timeout. |
| **dead** | A persisted outbox/spool operation is terminally failed and retained for bounded diagnosis/explicit handling. | A new graph object, an automatic infinite retry, or successful delivery. |
| **degraded** | A component/capability/model health attribute accompanying a result, such as cache recall or heuristic fallback. It can coexist with committed. | An item persistence state or proof of failure/success by itself. |
| **fail-open** | The host continues its ordinary conversation/model flow without Mebular injection or with delayed writes. | Data was written, recall was fresh, or a failure was hidden from diagnostics. |

### 3.2 Required transitions

```text
host attempt
  ├─ reject auth/mode/validation/quota ───────────────► failed (no new queue)
  └─ accepted
       ├─ extraction/conflict/host input outstanding ─► pending ─► failed/dead on bound
       ├─ durable local enqueue ──────────────────────► queued ──► failed/dead on bound
       │                                                   │
       │                                                   └─ capability write confirmed
       │                                                               │
       └─ capability write confirmed without queue ────────────────────┤
                                                                       ▼
                                                            local graph committed
                                                                       │
                                                             existing async sync
                                                             (not part of committed)
```

- A durable queue write must complete before a response says `queued=true` or returns HTTP 202 for queued work. A full/failed queue returns an explicit error; it must not return 202.
- **Outbox enqueue success = queued.** **Outbox replay success = committed only after capability write confirmation**, followed by active-entry removal. These are separate events.
- Capability `/version`, `/status`, health, authentication, or model success is not write confirmation. A write result must confirm the required IDs/operations; partial batch success cannot make the whole host operation committed.
- HTTP 200/2xx is transport success only. In particular, `extraction.status:'failed'` is failed and `extraction.status:'pending'` is pending regardless of 2xx. Host counters/status must distinguish transport handoff, extraction/settlement failure, pending, and graph commit.
- HTTP 202 means only non-final `pending` or `queued`, using existing response fields/reason codes. It must never be rendered as committed by a host or Console. `queued:false` host-extraction pending retains its bounded staging/recovery record; `queued:true` transfers durable replay ownership to the sidecar. A host spool may remove that entry after this explicit handoff, but its status must not claim graph settlement. If no durable record exists, pending work must have a finite in-process lifetime and an explicit failure exit.
- Record and detail writes are separate steps, not one transaction. Each object may become committed independently; overall ingest is committed only when every required object succeeds. A partial/failed/dead overall result must disclose any already-committed record rather than implying atomic rollback.
- A timeout after possible MCP commit is outcome-unknown. Reconcile/retry with the same idempotency key; never issue a new key for the same logical operation and never claim either definite success or definite non-commit without evidence.
- The original 202 response and its cached idempotency response are immutable historical outcomes, not a status-polling API. Final commit requires a subsequent authoritative read/list/checkpoint-revision result or another actual capability confirmation; replay does not retroactively rewrite the old HTTP response. Pending reconciliation itself must have a bounded failure exit.
- Checkpoint responses and host adapter status may show a committed revision only after graph confirmation. Existing staged/outbox data, cache, native host compaction, and a DSH session record do not qualify.

### 3.3 Common error disposition

| Condition | Target disposition |
|---|---|
| 400/403/422 validation/policy | No blind retry. Fail the attempt; an already persisted operation moves to dead with a sanitized reason. |
| 401 host token | Re-read the current discovery/token file and retry once with the same request ID. Explicit raw-token overrides require the operator to update the override. Persistent failure stays uncommitted and visible. |
| 401 capability token | Sidecar re-reads the current capability token once. Persistent failure becomes degraded and queued work remains bounded; mode revocation must not create new staging/outbox entries. |
| 409 `mode_mismatch` | Stop the immersive path; do not enqueue, inject, or grow spool. Existing pending data remains preserved or explicitly purgeable. |
| 409 `revision_mismatch` | For a **direct, non-queued host update**, GET current revision and retry once with the same logical update; a second conflict remains pending only with bounded recovery, then failed. For an **already queued replay**, do not GET/rebase onto a newer revision: apply §6.2 and become failed/dead visibly. Never blind-overwrite. |
| 409 `checkpoint_lease_held` | No forced agent overwrite. Retry cooperatively within a finite bound or fail visibly; only existing user/system governance may force. |
| 429 | Honor `Retry-After` and use a shared recall/write cooldown; no tight loop. Delayed writes remain pending/queued, never committed. `Retry-After` changes timing, not the operation's retry/deadline budget: DSH keeps at most two retries after the initial attempt, OpenCode at most two total ingest attempts, and Hermes' configured `sync_max_attempts` must become a real terminal bound rather than warning-only. |
| Timeout/network/5xx | Fail open for chat/recall. For writes, retry idempotently within explicit bounds; once durably accepted, sidecar outbox owns replay. Otherwise use the host-specific durable-or-failed rule in §7. |
| Process restart | Replay durable entries with the same key, or mark non-durable interrupted work failed/visible. Never leave an invisible permanent pending and never manufacture committed from local intent. |

### 4.2 Disable linearization and highest acceptance invariant

When the disable operation has completed and the host adapter has observed missing/disabled discovery or `mode_mismatch`:

1. No new ingest, extraction, host-candidate request, recall/context injection, Compact, Checkpoint, SelfRecord, staging item, outbox item, or Hermes spool item may be produced by immersive integration.
2. Existing staging/outbox/spool counts and payload bytes must not grow. Periodic local deletion is allowed and must be distinguishable from new writes. No outbox flush is part of disable.
3. Already committed graph objects remain. Nothing is labelled committed from a pending intent. Existing public MCP tools continue normally.
4. A stale adapter retry receives 401/409/explicit unavailability and fails open without persistence growth. Re-enable creates fresh authorization/discovery and only then resumes idempotent replay.
5. For attached/manual, the external PID may remain alive; this is intentional. The acceptance assertion is both **PID remains owned by the operator** and **zero immersive side effects**, not process death.
6. Managed process stop by itself is insufficient evidence: tests must also observe host model requests/listeners and filesystem queues. Local cleanup while an attached/manual process remains alive is allowed; cleanup while a managed process is stopped occurs on explicit purge or next compatible start.

For attached/manual, discovery deletion is only a host-discovery signal, not proof that a cached URL/token can no longer call the sidecar. **Clean disable** requires the sidecar to observe capability/mode revocation and enter dormant admission/replay/model behavior. If this cannot be confirmed, the outcome is **incomplete/degraded**, not clean; it cannot pass C08/C09 or the release lifecycle gate as a successful clean disable. Hosts must still fail open without immersive calls, and any observed side effect fails C09. Implementation must use the existing mode/capability/discovery surfaces; no new public control protocol is authorized. A clean-disable acceptance test also fails if cached credentials can create work after revocation has been observed.

### 4.3 Discovery and refresh

- Capability state, degraded reason, model state, and reachable state are separate observations with refresh or bounded re-probe. Process liveness is not capability readiness, model readiness, or write commit.
- MCP and all hosts apply the same discovery freshness thresholds (baseline: stale after 15 s, dead after 30 s) in addition to PID/health/profile/version checks. A live process with stale discovery is not ready.
- Missing, stale, wrong-profile/cloud, or wrong-instance discovery disables product calls rather than selecting a guessed port. Delete/rewrite only the discovery record owned by the matching instance. Read-only status/inspect calls never delete discovery; cleanup belongs to an explicit lifecycle/maintenance path with the same identity guard.
- Host token rotation invalidates cached bearer state; adapters re-read once and never log the token. Capability rotation never requires exposing that token to hosts or browser JavaScript. An environment value may bootstrap a child, but a 401 refresh must re-read the rotated capability-token file rather than reusing the stale environment value.
- Shutdown cleanup is fault-isolated: settlement/model disposal failure must still close HTTP and run matching discovery/token/lock cleanup. An explicit operator stop may use its documented bounded behavior; immersive disable itself never flushes.
- MCP restart must not leave a stale enabled snapshot forever. Recovery is bounded and visible as starting/degraded/failed until fresh checks succeed.

## 6. Offline objects, retention, and context

### 6.1 Compact

1. While capability is offline, a Compact request may become bounded pending/queued only after its source IDs have been resolved. Offline source discovery/selection without resolved source IDs fails explicitly; it is not queued as a placeholder. No Compact node with a title-only/empty/generated-placeholder body may be committed.
2. Persist enough non-authoritative request metadata to recover: resolved source IDs, expected source hashes when already known, domain, stable request ID, model/policy choice, and deadline. After capability recovery, re-read one current source set, verify domain and any expected hashes, produce an actual summary through the configured source or its documented heuristic degradation, and persist the hashes of that same source set with the summary, then write once idempotently.
3. If sources are unavailable, an expected hash changed, the deadline is exceeded, or summarization cannot produce a real body, fail/dead visibly. Without an expected old hash, recovery summarizes the newly read current set and commits its actual hashes rather than claiming the old set. Do not retry forever and do not commit a placeholder.
4. A committed Compact includes real content, non-empty `sourceIds`/`sourceHashes`, provenance, and accurate stale/degraded markers. Detail IDs are not Compact source IDs.

### 6.2 ContextCheckpoint revision and lease

- Revision is monotonic per existing checkpoint key. An update to an existing checkpoint must carry the last committed `expectedRevision`; creation of a new key uses the capability's existing create convention. Direct `expectedRevision` mismatch returns 409; the host performs one read-and-retry and then bounded pending/failed behavior.
- A queued replay does **not** silently rebase onto a newer revision. Revision conflict becomes visible failed/dead for explicit host/user regeneration; an active lease conflict may retry only within the lease/deadline bound and then fails/dead. No agent uses `force`.
- Pending cache and last-committed cache are distinct. Offline GET must label pending and must not present it as the last committed revision; where both views cannot be represented by the existing response, return the last committed object plus pending/degraded metadata rather than replacing it with pending intent.
- A lease defaults to the existing 60 s cooperative window and server-derived `hostId`. Expiry permits cooperative acquisition; it does not prove the prior host stopped and does not delete the checkpoint.
- `task:*` participants share a revision; `default` remains scoped logically by `(agentId, threadId)`. Reads do not require acquiring the write lease.
- This is local optimistic concurrency plus a cooperative hint across synced replicas, **not** strong cross-device consistency, distributed locking, exactly-once distributed execution, or agent authentication.
- A 202/pending checkpoint has no committed revision in host status. Restart either replays its durable state or records an explicit interrupted/failed outcome under §7. Destructive checkpoint/detail/Self operations are not newly queued: checkpoint/detail deletion is online-only, and Self has no delete in v0.3.2.

### 6.3 SelfRecord and `/context`

1. Retain the existing public `includeSelf` promise and make it real (D3). `includeSelf=true` must read the same logical agent's current SelfRecord; `false` injects none. A legitimately absent current SelfRecord produces a non-degraded empty result with no self block. A read failure, unavailable authority, or stale/unverifiable data returns explicit `degraded=true` and a stable reason, never a fabricated current/empty success; superseded revisions are never selected over the current revision. This target adds context consumption only, not a Self delete/TTL protocol.
2. Context order is **self → checkpoint → compact/fragment**, within existing byte/token budgets. No empty self/checkpoint block is injected. All memory text remains untrusted background, never instructions or tool calls.
3. Self reads use sidecar policy and current graph/cache freshness rules. A host token holder supplying another `agentId` is not a newly authenticated agent; no cross-agent claim is made.
4. `/context` actively reads the current checkpoint after compaction and on a new turn when requested. `summary_only` remains visibly degraded; expired/deleted checkpoints and superseded/unavailable Self cache cannot be re-injected as current.

### 6.4 Periodic maintenance

- Sidecar local maintenance runs on a bounded timer while the process is alive, including when no requests arrive, and also at startup. Tests must advance beyond at least one full cleanup interval without restarting or sending new ingest.
- MCP authoritative Detail maintenance runs while the daemon is alive and idle. Expiry is enforced at read time even before the tombstone pass.
- Maintenance is idempotent and bounded per pass, exposes last-run/error/count/bytes/oldest-age diagnostics without bodies, and cannot starve host requests or grow the queue it is meant to clean.
- Disabling immersive stops new work and replay; it does not require deleting committed objects. Local cleanup may continue in a live attached/manual process; managed-stopped data is cleaned on explicit purge or next start.

### 7.1 Common target

## 10. Chief resolutions and non-goals

### 10.1 Resolved decisions (binding)

| ID | Resolution | Binding target and consequence |
|---|---|---|
| **D1** | **Approved — 2026-11-04** | Attached/manual external processes belong to their operator. Immersive disable/MCP disposal does not kill or replace them; only the managed child owned by this MCP instance is terminated. Explicit operator CLI stop remains allowed. Disable never flushes pending writes. The external process must enter verifiable dormant behavior with zero immersive side effects; an unhealthy/incompatible external process is reported to its operator, not killed/replaced. |
| **D2** | **Approved — 2026-11-04** | Sidecar outbox and Hermes spool have a **30-day maximum queued age**, or earlier operation expiry, followed by visible dead/failed handling. Sidecar dead entries remain 30 d and are periodically cleaned. Long-offline unsettled work is not guaranteed delivery. WP1/WP4b use this shared value; no adapter-specific silent drift is allowed. |
| **D3** | **Approved — 2026-11-04** | Retain `includeSelf`; WP3 must implement actual SelfRecord consumption in `/context`, including the absence/error semantics in §6.3. Silently returning fake empty success is forbidden. |
| **D4** | **Approved — 2026-11-04** | Hermes provider-through-stub is adapter evidence only. A real Hermes host claim requires a real Hermes process. If that prerequisite is unavailable, the corresponding release claim remains incomplete; neither the harness nor an execution session may waive it. |
| **D5** | **Rejected — 2026-11-04** | Add no raw-detail Console by-ID proxy and no new raw-detail route; do not expand the interface surface. Keep the absence of a raw-detail Console proxy, calibrate/narrow the historical raw-detail governance design promise (`docs/design/0.3.0-immersive-product-contract.md:359-409`) in the coordinated documentation task, and leave existing generic internal-object governance unchanged. No alternative proxy branch is authorized. |
| **D6** | **Approved — 2026-11-04** | Sanitized status/trace/model reads use `memory.read`. All Console/MCP proxy mutations use `memory.admin` + existing origin/CSRF/`writes-enabled` controls. With D5 rejected, no new raw-detail route exists. Direct sidecar access still has only the all-powerful host token and gains no role separation. |

All six resolutions are final for v0.3.2 and binding on WP1–WP6. Execution sessions must not choose an alternative branch or grant a local waiver; any later change requires new chief/user change control.

### 10.2 Already bounded, not new feature requests

- DSH 0.2.1-rc.2 durable context copy remains a disclosed host limitation. v0.3.2 does not promise request-only DSH injection or Mebular-driven erasure of that file.
- DSH/OpenCode still have no durable host ingest spool. The target is bounded, visible failure before sidecar acceptance plus durable sidecar replay after acceptance, not a new host storage subsystem.
- No multi-user accounts, namespace ACLs, per-agent cryptographic isolation, strong cross-device Checkpoint consistency, guaranteed remote erasure, new host/model source, or new public MCP/API protocol is added.
- No new SelfRecord delete/TTL operation, offline detail/checkpoint delete queue, default 30-day authoritative Checkpoint expiry, or forward-detail record rewrite is introduced. Existing graph/event/history formats remain unchanged.
- No historical acceptance report, CHANGELOG, DSH package README, or existing v0.3.0 user guide is rewritten by WP0. Later user-facing calibration is a separate coordinated integration task after behavior exists.
