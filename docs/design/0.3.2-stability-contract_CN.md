# Mebular v0.3.2 运行时稳定性契约

> **状态：** 供负责人评审的 WP0 候选稿；不是实现报告或验收报告。
> **日期：** 2026-11-03
> **基线：** `beba4f35c7f001d6109f1bb02fdce1cb67dc3133`（`origin/main`，包含文档校准 PR #304）。
> **集成基线：** 同一 SHA 上的 `feat/0.3.2-stability`。
> **English:** [English](0.3.2-stability-contract.md).

本文是 v0.3.2 WP1–WP6 的唯一行为目标。英文和中文文件使用相同的契约 ID；措辞差异属于文档缺陷，并不允许实现不同的行为。本文不取代历史 v0.3.0 报告或用户指南。

## 0. 如何阅读本契约

- **基线事实**描述基线 SHA 上的源码、测试或经过校准的文档。它并不声称该行为是正确的。
- **目标**是负责人批准后 v0.3.2 必须具备的行为。它并不声称该行为已经存在或已经通过测试。
- **证据**指明能够判定通过/失败的测试。历史结果不会成为新 SHA 的证据。
- **必须/不得**具有规范性。**建议**表示仍需负责人在 §10 批准的产品权衡；它不是执行会话可以自行选择的实现方案。

以下既有边界保持不变：

1. 保留 29 个公共 MCP 工具及其现有语义。不得新增公共 `runtime_*` 工具、宿主、模型来源、同步线路协议、事件类型、第二记忆存储或跨设备一致性协议。
2. MCP 守护进程拥有图、事件日志、同步和能力 API。sidecar 不得直接写图。
3. 轻量 MCP 仍是默认模式，不启动 sidecar、采集、模型下载或远程模型调用。
4. 信任模型仍是一个云和一个用户。`agentId`、域参与关系和租约所有权都是逻辑断言，不是认证、命名空间 ACL 或密码学的 agent 隔离。
5. 本地图提交不等于远程同步。墓碑传播是协作式的；任何 Mebular 操作都不保证在离线对端、宿主自有的文件或模型提供方日志中物理擦除。
6. 不授权大规模 Console 重设计或全仓库重写。如果目标无法在这些边界内实现，必须停止并走负责人变更控制，而不是编造并行契约。

### 2.3 数据最小化与证据关联

1. 在 staging、outbox、Hermes spool、日志/状态或远程模型请求之前进行脱敏和最小化。仅持久化抽取、幂等重放、保留和诊断所需的字段。
2. 多域抽取必须为每个域选择实际提供支撑的 chunk/message ID。不得把整个请求中无关的 chunk 复制到每个域。如果同一证据确实支撑两个域，则创建各自独立的同域 DetailRecord，各自具有自己的 ID 和引用。
3. 规范的 record↔detail 关联是经过验证的同域 `DetailRecord.recordIds` 加现有反向查询。不得仅为反规范化 `provenance.detailIds` 而在沉淀后重写 MemoryRecord；基线 capability 会丢弃该前向字段。如果存在旧版/提供的前向字段，它必须一致，且不得被宣传为唯一查询方式。`rawChunkIds` 仍是兼容性元数据，不是图 Detail ID 的 staging-ID 替代品。
4. Checkpoint `recordIds/detailIds` 和 `state.references` 图 ID 必须在 capability 提交时验证存在性、预期类型、存活状态和同域；无效的 queued 引用必须 failed/dead，而不是提交悬空证据。外部消息 ID 仍是宿主引用，不是图证明。没有证据就不得编造关联。
5. `tool` role 或 `detailKind=tool_output` 选择 `tool_output`；`document_slice` 选择 `document_slice`；普通 user/assistant/system 对话使用 `conversation`；`pinned` 需要显式治理。Runtime 和 core 的 detail-kind 枚举必须与 core/规范集合匹配。服务端策略可以缩短保留期，但绝不得静默延长。`retentionClass` 仅适用于 DetailRecord，不适用于 Compact/Checkpoint/SelfRecord。
6. 权威 Detail 过期不会删除 MemoryRecord、Compact、Checkpoint 或 SelfRecord。本地进程清理绝不会删除图对象。Detail 治理删除在 v0.3.2 中仍仅在线进行；不新增离线 sidecar detail-delete 生产者。
7. **图删除不是物理内容擦除。** 基线 create/update 事件包含完整节点版本，被标记墓碑的节点仍保留内容（`src/core/GraphStore.ts:60-73,100-111,162-192`）。同样的披露适用于已同步快照、旧 Checkpoint/Self revision、Compact 历史、outbox/dead 正文和 capability 幂等账本。v0.3.2 必须测试并记录这些副本，而不是声称安全/本地擦除；更改该事件/历史格式超出范围。
8. 清理必须感知依赖关系。如果活动 outbox/pending 操作仍需要 staging 证据，清理必须先使该依赖操作在其较早截止时间显式 failed/dead，或完成其沉淀；不得删除 staging 后又提交一个声称完整却静默缺失 Detail 的 ingest。部分对象提交遵循 §3 并保持显式部分提交。

## 3. 持久化与失败状态机

### 3.1 目标词汇

| 术语 | 确切含义 | 不得表示 |
|---|---|---|
| **accepted（已接受）** | 认证、模式、schema 和准入检查已通过；处理已开始。它是入口观察结果，不是持久化结果。 | 已排队、图已提交或已远程同步。 |
| **pending（待完成）** | 非最终工作仍需要抽取、宿主候选、capability 响应或冲突解决。任何在响应之后仍然存在的用户可见 pending 都必须有持久恢复记录，或有有界的失败转换。 | 已提交、默认无限重试，或请求已到达 MCP 的证明。 |
| **queued（已排队）** | 在宿主收到确认之前，某个具体 pending 操作已使用稳定幂等键原子地持久化到 sidecar outbox 或已披露的宿主 spool。 | 图写入成功。 |
| **committed（已提交）** | MCP capability 对每一项必需写入都返回成功，且对象已存在于本地图/事件日志中。只有当 `duplicate` 解析为同一幂等逻辑对象时，它才计入 committed。 | 仅已 staging、仅已入队、进程健康、capability 可达或已同步到对端。 |
| **failed（已失败）** | 本次尝试/操作达到终态、显式失败，且不会自动重试。 | 在含糊超时后，把可能成功或结果未知的提交重新标记为确定不存在。 |
| **dead（死信）** | 已持久化的 outbox/spool 操作已终态失败，并保留用于有界诊断/显式处理。 | 新图对象、自动无限重试或成功投递。 |
| **degraded（已降级）** | 伴随结果的组件/capability/模型健康属性，例如缓存召回或启发式回退。它可以与 committed 同时存在。 | 条目持久化状态，或它本身作为失败/成功的证明。 |
| **fail-open（失败开放）** | 宿主在没有 Mebular 注入或延迟写入的情况下继续其普通对话/模型流程。 | 数据已写入、召回是新鲜的，或失败未显示在诊断中。 |

### 3.2 必需转换

```text
宿主尝试
  ├─ 拒绝认证/模式/验证/配额 ───────────────────────► failed（不新建队列）
  └─ accepted
       ├─ 抽取/冲突/宿主输入尚未完成 ────────────────► pending ─► 到达界限时 failed/dead
       ├─ 本地持久入队 ──────────────────────────────► queued ──► 到达界限时 failed/dead
       │                                                   │
       │                                                   └─ capability 写入已确认
       │                                                               │
       └─ 未经队列的 capability 写入已确认 ────────────────────────────┤
                                                                       ▼
                                                            本地图 committed
                                                                       │
                                                             现有异步同步
                                                             （不属于 committed）
```

- 持久队列写入必须先完成，响应才能声明 `queued=true` 或为已排队工作返回 HTTP 202。队列已满/失败时必须返回显式错误；不得返回 202。
- **outbox 入队成功 = queued。** **outbox 重放成功只有在 capability 写入确认后才 = committed**，随后移除活动条目。这些是两个独立事件。
- capability `/version`、`/status`、健康检查、认证或模型成功都不是写入确认。写入结果必须确认所需的 ID/操作；部分批次成功不能使整个宿主操作成为 committed。
- HTTP 200/2xx 仅表示传输成功。特别是，无论是否为 2xx，`extraction.status:'failed'` 都是 failed，`extraction.status:'pending'` 都是 pending。宿主计数器/状态必须区分传输交接、抽取/沉淀失败、pending 和图提交。
- HTTP 202 仅表示非最终的 `pending` 或 `queued`，使用现有响应字段/原因码。宿主或 Console 绝不能把它呈现为 committed。`queued:false` 的宿主抽取 pending 保留其有界 staging/恢复记录；`queued:true` 把持久重放所有权转移给 sidecar。在此显式交接后，宿主 spool 可以移除该条目，但其状态不得声称图已沉淀。如果没有持久记录，pending 工作必须具有有限的进程内生命周期和显式失败退出。
- 记录和 Detail 写入是独立步骤，不是一个事务。每个对象可以独立变为 committed；只有每个必需对象都成功时，整体 ingest 才是 committed。partial/failed/dead 的整体结果必须披露任何已提交记录，而不是暗示原子回滚。
- 可能已经在 MCP 提交之后发生的超时属于结果未知。使用相同幂等键进行对账/重试；绝不能为同一逻辑操作签发新键，也不能在没有证据时声称确定成功或确定未提交。
- 原始 202 响应及其缓存的幂等响应是不可变的历史结果，不是状态轮询 API。最终提交需要后续权威 read/list/checkpoint-revision 结果或另一个实际 capability 确认；重放不会追溯改写旧 HTTP 响应。pending 对账本身必须有有界失败退出。
- Checkpoint 响应和宿主适配器状态只有在图确认后才能显示已提交的 revision。现有 staging/outbox 数据、缓存、宿主原生压缩和 DSH 会话记录都不符合条件。

### 3.3 通用错误处置

| 条件 | 目标处置 |
|---|---|
| 400/403/422 验证/策略 | 不得盲目重试。使本次尝试失败；已持久化的操作带脱敏原因移入 dead。 |
| 401 宿主 token | 重新读取当前 discovery/token 文件，并使用相同请求 ID 重试一次。显式原始 token 覆盖要求操作者更新覆盖值。持续失败保持未提交且可见。 |
| 401 capability token | sidecar 重新读取当前 capability token 一次。持续失败变为 degraded，queued 工作保持有界；模式撤销不得创建新的 staging/outbox 条目。 |
| 409 `mode_mismatch` | 停止沉浸式路径；不得入队、注入或增长 spool。现有 pending 数据保持保留，或可被显式清除。 |
| 409 `revision_mismatch` | 对于**直接、非 queued 的宿主更新**，GET 当前 revision，并使用同一逻辑更新重试一次；第二次冲突只有在具有有界恢复时才保持 pending，随后 failed。对于**已 queued 的重放**，不得 GET/rebase 到更新的 revision：应用 §6.2 并显式变为 failed/dead。绝不能盲目覆盖。 |
| 409 `checkpoint_lease_held` | 不得强制进行 agent 覆盖。在有限界限内协作重试或显式失败；只有现有用户/系统治理可以强制。 |
| 429 | 遵守 `Retry-After`，并使用共享召回/写入冷却；不得紧密循环。延迟写入保持 pending/queued，绝不是 committed。`Retry-After` 改变的是时序，而不是操作的重试/截止时间预算：DSH 在首次尝试后最多重试两次，OpenCode 总共最多进行两次 ingest 尝试，Hermes 配置的 `sync_max_attempts` 必须成为真正的终态界限，而不是仅发出警告。 |
| 超时/网络/5xx | 对话/召回采用 fail-open。写入在显式界限内幂等重试；一旦持久接受，由 sidecar outbox 负责重放。否则使用 §7 中宿主特定的持久化或失败规则。 |
| 进程重启 | 使用相同键重放持久条目，或将非持久的中断工作标记为 failed/visible。绝不能留下不可见的永久 pending，也绝不能根据本地意图伪造 committed。 |

## 4. Sidecar 所有权与生命周期

### 4.1 所有权矩阵（目标）

| 模式 | 所有权与启动 | 热禁用 | MCP 重启 / sidecar 重启 | Token 与 discovery |
|---|---|---|---|---|
| **managed** | 仅在 immersive 启用时，MCP supervisor 才派生子进程，并只记录该子进程的身份。 | 撤销 capability，停止准入/重放/模型工作，在有界等待内优雅停止所拥有的子进程，随后仅在需要时终止该子进程。**禁用期间不得冲刷 queued 写入。** 移除匹配的 discovery，并轮换/撤销凭据。 | MCP 重启时，由父进程监督使已过期的所属子进程退出；仅在启用时启动新子进程。sidecar 重启会轮换宿主 token；capability 401 导致一次 token 文件重读。仅在启用且获授权时恢复持久重放。 | 生产宿主 token 是 `host-token` 中的 JSON 记录（`0600`）。discovery 包含 `tokenFile`，而不是 token 值。只有在实例/配置文件身份匹配后才移除陈旧 discovery。 |
| **attached** | 在 URL/配置文件/云/版本/新鲜度验证后，连接到已在运行且兼容的 sidecar。MCP 没有派生它，也不拥有其 PID。不健康/不兼容的外部进程变为 degraded/failed，并交由其操作者处理；MCP 不得终止或替换它。 | **不得停止、SIGTERM 或 SIGKILL 外部进程（D1）。** 撤销/断开此云的 capability，移除/禁用匹配的 discovery，并使宿主 API/适配器休眠。不冲刷，也不产生新的本地工作。 | MCP 重启仅在启用时重新连接，并签发/使用当前 capability 凭据。外部 sidecar 重启通过 discovery 和 token 重读恢复；MCP 不会自动终止它。 | 为 Console 代理和适配器解析真实 JSON host-token 文件。原始 token 仅用于显式测试/手动覆盖。陈旧/不匹配的 discovery 表示禁用，绝不能盲目连接。 |
| **manual** | 操作者启动 `mebular-memory-runtime`；Mebular 可以发现/连接，但绝不声称拥有该进程。不健康/不兼容/manual 不匹配遵循相同的不终止/不替换规则。 | **不得停止外部进程（D1）。** 应用与 attached 相同的 capability 撤销、discovery 失效、准入停止、重放停止和不冲刷规则。 | MCP 重启不会重启或终止 manual 进程。仅在启用时显式重新连接到兼容实例后，才重新授权/重放。 | 与 attached 相同的 JSON/原始 token 和身份规则。显式环境/原始 token 配置的轮换由操作者负责。 |

### 4.2 禁用线性化与最高验收不变量

当禁用操作已完成，且宿主适配器已观察到 discovery 缺失/禁用或 `mode_mismatch` 时：

1. 沉浸式集成不得产生新的 ingest、抽取、宿主候选请求、召回/上下文注入、Compact、Checkpoint、SelfRecord、staging 项、outbox 项或 Hermes spool 项。
2. 现有 staging/outbox/spool 的计数和负载字节数不得增长。允许周期性本地删除，且必须能与新写入区分。禁用不包含 outbox 冲刷。
3. 已提交的图对象保持存在。不得根据 pending 意图把任何内容标记为 committed。现有公共 MCP 工具继续正常运行。
4. 陈旧适配器重试会收到 401/409/显式不可用，并在没有持久化增长的情况下 fail-open。重新启用会创建新的授权/discovery，只有此后才恢复幂等重放。
5. 对 attached/manual，外部 PID 可以继续存活；这是有意设计。验收断言同时是 **PID 仍由操作者拥有**和**零沉浸式副作用**，而不是进程死亡。
6. 仅凭 managed 进程停止不足以作为证据：测试还必须观察宿主模型请求/监听器和文件系统队列。attached/manual 进程仍存活时允许本地清理；managed 进程停止后的清理由显式清除或下一次兼容启动触发。

对 attached/manual，删除 discovery 只是宿主发现信号，并不能证明缓存的 URL/token 无法再调用 sidecar。**干净禁用**要求 sidecar 观察到 capability/模式撤销，并进入休眠准入/重放/模型行为。如果无法确认这一点，结果就是**不完整/degraded**，而不是干净禁用；它不能作为成功的干净禁用通过 C08/C09 或发布生命周期门禁。宿主仍必须 fail-open 且不进行 immersive 调用，任何观察到的副作用都会使 C09 失败。实现必须使用现有 mode/capability/discovery 接口面；不授权新增公共控制协议。如果在观察到撤销后，缓存凭据仍能创建工作，干净禁用验收测试也会失败。

### 4.3 Discovery 与刷新

- capability 状态、degraded 原因、模型状态和可达状态是独立观察结果，需要刷新或有界重新探测。进程存活不等于 capability 就绪、模型就绪或写入已提交。
- 除 PID/健康/配置文件/版本检查外，MCP 和所有宿主应用相同的 discovery 新鲜度阈值（基线：15 秒后 stale，30 秒后 dead）。进程存活但 discovery 陈旧时不就绪。
- discovery 缺失、陈旧、配置文件/云错误或实例错误时，必须禁用产品调用，而不是选择猜测的端口。只删除/重写匹配实例所拥有的 discovery 记录。只读 status/inspect 调用绝不删除 discovery；清理由具有相同身份保护的显式生命周期/维护路径负责。
- 宿主 token 轮换会使缓存的 bearer 状态失效；适配器重读一次且绝不记录 token。capability 轮换绝不要求向宿主或浏览器 JavaScript 暴露该 token。环境值可以引导子进程启动，但 401 刷新必须重读已轮换的 capability-token 文件，而不是复用陈旧的环境值。
- 关闭清理必须隔离故障：沉淀/模型处置失败时仍必须关闭 HTTP，并执行匹配的 discovery/token/lock 清理。显式操作者停止可以采用其记录在案的有界行为；immersive 禁用本身绝不冲刷。
- MCP 重启不得永久留下陈旧的 enabled 快照。恢复必须有界，并在最新检查成功前显式显示 starting/degraded/failed。

## 6. 离线对象、保留与上下文

### 6.1 Compact

1. capability 离线时，只有在 Compact 请求的来源 ID 已解析后，它才可以成为有界 pending/queued。没有已解析来源 ID 的离线来源发现/选择必须显式失败；不得作为占位符排队。不得提交正文只有标题/为空/生成占位符的 Compact 节点。
2. 持久化足够的非权威请求元数据以便恢复：已解析的来源 ID、已知时的预期来源哈希、域、稳定请求 ID、模型/策略选择和截止时间。capability 恢复后，重新读取一个当前来源集合，验证域和任何预期哈希，通过配置的来源或其记录在案的启发式降级生成实际摘要，并将该同一来源集合的哈希与摘要一起持久化，然后幂等地写入一次。
3. 如果来源不可用、预期哈希已改变、超过截止时间，或摘要无法生成真实正文，则显式 failed/dead。如果没有预期的旧哈希，恢复会摘要新读取的当前集合并提交其实际哈希，而不是声称使用旧集合。不得永远重试，也不得提交占位符。
4. 已提交的 Compact 包含真实内容、非空 `sourceIds`/`sourceHashes`、来源信息以及准确的 stale/degraded 标记。Detail ID 不是 Compact 来源 ID。

### 6.2 ContextCheckpoint revision 与 lease

- revision 按现有 checkpoint 键单调递增。更新现有 checkpoint 必须携带最后提交的 `expectedRevision`；创建新键使用 capability 的现有 create 约定。直接 `expectedRevision` 不匹配返回 409；宿主执行一次读取并重试，随后进入有界 pending/failed 行为。
- queued 重放**不会**静默 rebase 到更新的 revision。revision 冲突变为显式 failed/dead，由宿主/用户显式重新生成；活动 lease 冲突只能在 lease/截止界限内重试，随后 failed/dead。任何 agent 都不得使用 `force`。
- Pending 缓存和最后提交缓存是分离的。离线 GET 必须标记 pending，且不得把它呈现为最后提交的 revision；如果现有响应无法同时表示两个视图，则返回最后提交的对象加 pending/degraded 元数据，而不是用 pending 意图替换它。
- lease 默认使用现有 60 秒协作窗口和服务端派生的 `hostId`。过期允许协作获取；它不能证明前一个宿主已停止，也不会删除 checkpoint。
- `task:*` 参与者共享一个 revision；`default` 仍按 `(agentId, threadId)` 进行逻辑隔离。读取不需要获取写入 lease。
- 这是本地乐观并发加跨同步副本的协作提示，**不是**强跨设备一致性、分布式锁、恰好一次的分布式执行或 agent 认证。
- 202/pending checkpoint 在宿主状态中没有已提交的 revision。重启要么重放其持久状态，要么按照 §7 记录显式 interrupted/failed 结果。破坏性 checkpoint/detail/Self 操作不会被新排队：checkpoint/detail 删除仅在线进行，Self 在 v0.3.2 中没有 delete。

### 6.3 SelfRecord 与 `/context`

1. 保留现有公共 `includeSelf` 承诺并使其真正生效（D3）。`includeSelf=true` 必须读取同一逻辑 agent 的当前 SelfRecord；`false` 不注入任何 SelfRecord。合法不存在的当前 SelfRecord 产生非 degraded 的空结果，且不含 self 块。读取失败、权威来源不可用或数据陈旧/无法验证时，返回显式 `degraded=true` 和稳定原因，绝不伪造当前/空成功；绝不选择已被取代的 revision 而非当前 revision。此目标仅新增上下文消费，不新增 Self delete/TTL 协议。
2. 上下文顺序为 **self → checkpoint → compact/fragment**，并遵守现有字节/token 预算。不得注入空的 self/checkpoint 块。所有记忆文本仍是不可信背景，绝不是指令或工具调用。
3. Self 读取使用 sidecar 策略和当前图/缓存新鲜度规则。提供另一个 `agentId` 的 host token 持有者不是新认证的 agent；不作跨 agent 声明。
4. `/context` 在压缩后以及请求的新轮次中主动读取当前 checkpoint。`summary_only` 保持显式 degraded；过期/删除的 checkpoint 和已被取代/不可用的 Self 缓存不能作为当前内容重新注入。

### 6.4 周期性维护

- sidecar 本地维护在进程存活期间按有界计时器运行，包括没有请求到达时，也在启动时运行。测试必须在不重启且不发送新 ingest 的情况下推进至少一个完整清理间隔。
- MCP 权威 Detail 维护在守护进程存活且空闲时运行。即使在墓碑遍历之前，读取时也会执行过期检查。
- 维护是幂等的，每趟有界，暴露 last-run/error/count/bytes/oldest-age 诊断但不暴露正文，不能使宿主请求饥饿，也不能增长它本应清理的队列。
- 禁用 immersive 会停止新工作和重放；不要求删除已提交对象。在仍存活的 attached/manual 进程中可以继续本地清理；managed 停止后的数据在显式清除或下次启动时清理。

## 7. 共享宿主失败语义

### 7.1 共同目标

| 事件 | DSH | Hermes | OpenCode / OpenChamber |
|---|---|---|---|
| 超时 / sidecar 不可用 | 在没有当前记忆块的情况下继续对话。有界幂等 ingest 重试；在现有两次网络重试之后，如果从未被接受则显式丢弃。Checkpoint 不 committed。 | 召回返回空并应用冷却。持久 ingest spool 保留有界工作；checkpoint 遵循持久重放或显式有界失败，绝不静默永久 pending。 | 在没有记忆块的情况下继续模型请求并应用冷却。有界内存 ingest 如果从未被接受则显式丢弃；checkpoint 不 committed。 |
| 401 | 使用相同请求 ID 刷新当前 JSON host token 一次。持续失败是可见的/未提交的。 | 重读一次；召回为空，queued 写入保持有界。持续模式/认证失败不得导致无限重试。 | 重读一次；不注入，有界写入处理，状态/日志/会话中不得出现 token。 |
| 429 / 5xx | 遵守 `Retry-After`；共享冷却/退避；不得根据重试接受产生 committed 状态。 | 相同；spool 重放使用有界退避，不得紧密循环。 | 相同；事件/重试循环保持有界且不阻塞模型流程。 |
| Revision 不匹配 / lease 冲突 | 一次当前 revision GET + 一次重试；随后显式 pending/failed。不得盲目压缩覆盖。 | 相同；pending 必须具有有界重启语义。 | 相同；一次读取并重试，随后显式 pending/failed。 |
| 进程/宿主重启 | 不声称存在宿主持久 ingest/checkpoint spool。sidecar 已接受的 202 工作从 sidecar outbox 重放；接受前中断的工作被显式丢弃/标记失败，而不是永远 pending。 | 重新打开单写者 spool，并使用稳定 ID 重放 ingest **和 checkpoint** 条目。Checkpoint pending 必须在 pending 确认之前持久化到该现有 spool；如果持久化失败，则报告 failed，而不是接受仅存在于内存中的 pending。 | 事件流断开后重新订阅。不声称存在持久宿主 spool；非持久的中断 pending 变为 failed/visible。sidecar 已接受的工作仍会重放。 |
| 热禁用 | 停止监听器驱动的 ingest、召回、维护候选和 checkpoint 写入；不新建队列。DSH 可以保留其外部进程/原生会话。 | 停止预取/同步/checkpoint/spool 增长；现有 spool 保留但不冲刷。`mode_mismatch` 不得按暂时性故障重试。 | 取消事件订阅/计时器且不注入任何内容；不产生新的内存工作或 sidecar 队列。原生 OpenChamber 文件保持不变。 |

Fail-open 始终指宿主对话。它绝不抑制诊断，也不把写入转换为 committed。宿主在持久性上的差异必须保持明确，不得隐藏在共同的绿色状态之后。

### 7.2 宿主特定不变量

- **DSH：** 只有在图确认 revision 后，checkpoint 才是 committed。保留有界重试、429 处理、召回冷却、失败可见性以及已披露的持久 `session.v4.jsonl` 副本。轻量模式仍可执行检测重新启用所需的实际最小监听器/discovery 轮询；文档不得声称绝对没有注册/轮询。必须声称零沉浸式 ingest/recall/queue 副作用。
- **Hermes：** 保留持久有界 spool 和单写者规则。对齐认证、暂停/冷却、重试和失败报告。不得修改内置 `MEMORY.md`/`USER.md`。MemoryProvider 和可选 companion 只使用现有宿主/模型接缝；不承诺隐藏的远程 provider、额外 provider 槽位或新模型来源。
- **OpenCode/OpenChamber：** 断开后恢复事件流订阅，并采用有界去重重放。配置键必须影响实际请求，否则必须移除/显式拒绝；被忽略的 `enabled`/domain/recall-limit 类键不得伪装成有效控件。保持仅请求内 `trust=untrusted`、不导入/双写原生记忆以及 MCP 配置边界。插件 `modelSource` 和 Console 模型来源彼此独立，除非存在实际实现的映射；不声称自动跟随三个宿主。

## 8. 验收证据规则

### 8.1 Real、fake、stub、fallback 与 skip

| 标签 | 允许的声明 | 门禁处理 |
|---|---|---|
| **real component（真实组件）** | 指定的生产组件确实运行了：真实图/capability、真实 sidecar、真实宿主进程或真实模型，每项分别列出。 | 真实组件声明需要标识该组件及其版本的日志/产物。真实图不意味着真实宿主；真实宿主不意味着真实模型。 |

### 8.2 报告要求

每项 v0.3.2 结果都绑定完整候选 SHA 和 dirty 状态、确切命令、OS/架构、适用的 Node/Python、宿主和模型/模型包版本、开始/结束结果、executed/passed/failed/skipped 计数、real/fake/stub 边界，以及脱敏的机器可读产物。不得包含 token、机密、原始用户内容或真实用户 home 路径。

CI/nightly/release 路径过滤器必须包含 sidecar 和宿主变更。仅 nightly 或手动触发的套件必须如此标记，且不意味着每个 PR 都有覆盖。包含必需 skip 的绿色 workflow job 不足以作为相应真实门禁的证据。

| **D5** | 为满足现有原始 Detail 治理设计承诺（`docs/design/0.3.0-immersive-product-contract.md:359-409`），只新增一个 `memory.admin` 按 ID 读取原始 Detail 的 Console 代理；不提供原始 Detail 列表，也不新增专用原始 checkpoint/self 代理。 | 基线没有原始 Detail 代理。负责人必须决定此最小内部 Console 管理员路由是否属于 WP2 范围，或是否必须缩小现有原始 Detail 承诺。它不新增公共 MCP 工具、宿主 API、同步协议或事件类型；如果负责人认为任何新增管理员路由都是未经授权的公共 API 扩展，则必须采用无代理/缩小承诺分支。执行会话不得静默新增宽泛的 detail/checkpoint/self 代理接口面。 |
| **D6** | 脱敏的 trace/model/status 读取保持为 `memory.read`；所有变更和任何原始 Detail 治理保持为 `memory.admin`，并采用现有 origin/CSRF/写入控制。 | 当前代码/测试对 trace 使用 `memory.read`，而较早的设计将其标记为 admin。负责人必须在 WP2 前批准校准后的读取边界。直接 sidecar 访问仍只有全能 host token，不获得角色分离。 |

### 10.2 已有边界，不是新功能请求

- DSH 0.2.1-rc.2 持久上下文副本仍是已披露的宿主限制。v0.3.2 不承诺仅请求内 DSH 注入或由 Mebular 驱动擦除该文件。
- DSH/OpenCode 仍没有持久宿主 ingest spool。目标是在 sidecar 接受前提供有界、显式失败，在接受后提供持久 sidecar 重放，而不是新宿主存储子系统。
- 不新增多用户账户、命名空间 ACL、按 agent 的密码学隔离、强跨设备 Checkpoint 一致性、保证远程擦除、新宿主/模型来源或新公共 MCP/API 协议。
- 不引入新的 SelfRecord delete/TTL 操作、离线 detail/checkpoint 删除队列、默认 30 天权威 Checkpoint 过期或前向 Detail 记录重写。现有图/事件/历史格式保持不变。
- WP0 不重写任何历史验收报告、CHANGELOG、DSH 包 README 或现有 v0.3.0 用户指南。后续面向用户的校准是在行为存在后单独协调的集成任务。
