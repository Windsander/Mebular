# Memory Runtime guide (0.3.0)

[中文](MEMORY_RUNTIME_CN.md) · [Documentation index](../README.md) · [Acceptance report](../quality/0.3.0-memory-runtime-acceptance.md)

Mebular 0.3 adds an optional **Memory Runtime sidecar** next to MCP. It can ingest
conversation slices, extract candidates, recall fragments, assemble a context block and
store task checkpoints for a host. It is **one extra layer over the same graph**, not a
second memory database.

The default is unchanged: **lightweight MCP**. A host that only needs explicit
`memory_*` / `task_*` tools never starts the sidecar. The immersive path is an explicit,
per-device opt-in.

```text
┌──────────────────────────────────────────────────────────────────┐
│ Host / Agent                                                     │
│   lightweight: MCP client ─────────────► /mcp (29 tools)          │
│   immersive:   host adapter ───────────► /memory-runtime/v1       │
└───────────────────────┬──────────────────────────┬───────────────┘
                        │                          │
                        ▼                          ▼
          ┌──────────────────────────┐   ┌──────────────────────────┐
          │ MCP daemon               │   │ Memory Runtime sidecar   │
          │ 29 public MCP tools      │◄──┤ ingest / recall / context│
          │ MemoryService            │   │ compact / self / trace   │
          │ Graph + EventLog + sync  │   │ Raw / Trace / cache /    │
          │ /internal/memory/v1      │   │ outbox / model settings  │
          └────────────┬─────────────┘   └──────────────────────────┘
                       │
                       ▼
          existing graph + signed events + sync + your cloud
```

The sidecar is a **separate process** (`mebular-memory-runtime serve`) and a separate
package (`@mebular/memory-runtime`). It has no write path to the graph. Every durable
object goes through the internal MCP capability API (`/internal/memory/v1`) into the
existing `GraphStore` / `EventLog`; the existing sync layer then carries it to the other
devices in your cloud (忆云). MCP remains the only graph writer.

This guide covers the user-facing behaviour. The frozen design is in
[contract v2](../design/0.3.0-memory-runtime-contract-v2.md),
[sidecar lifecycle](../design/0.3.0-memory-runtime-sidecar.md) and
[fragmented recall](../design/0.3.0-fragmented-recall.md).

## Lightweight MCP vs immersive sidecar

| | Lightweight MCP (default) | Immersive Memory Runtime |
|---|---|---|
| Process | MCP daemon only | MCP daemon + sidecar |
| Who decides what to remember | The host model, through tools | The sidecar, from what the host explicitly sends |
| Public tools | 29 `memory_*` / `task_*` tools | Same 29 tools; no new public tool |
| Automatic recall | No | Opt-in, request-only, at most once per human turn |
| Raw conversation | Not captured | `capture=off` by default; `capture=local` only when explicitly requested |
| Model | None by Mebular | Only the source you configure; `heuristic` by default |
| Durable data | Existing graph + events + sync | Same graph + events + sync, written through capability |

Both modes read and write the **same** Mebular memory. Switching modes does not copy,
migrate, rewrite or delete nodes. Mode is device-local: one device can stay lightweight
while another device in the same cloud uses the sidecar.

## Turn it on

Prerequisites:

- Node.js 20 or newer.
- An **HTTP** MCP daemon (`mebular serve`) on this device. Stdio `mebular mcp` does not
  start the sidecar.
- The sidecar executable installed separately. Mebular does not download it for you.
  Install `@mebular/memory-runtime@0.3.0` (`npm install -g @mebular/memory-runtime`) so
  `mebular-memory-runtime` is on `PATH`, or point `memoryRuntime.command` at an absolute
  executable path.

1. Enable the MCP lifecycle switch, in **Console → Settings → 记忆运行时**, or in
   `<home>/config.json`:

   ```jsonc
   {
     "memoryRuntime": {
       "enabled": true
     }
   }
   ```

2. Start (or restart) `mebular serve`. The daemon mounts `/internal/memory/v1`, creates a
   capability token, and asynchronously starts the sidecar. Automatic startup is
   non-blocking: MCP readiness, the 29 tools, sync and authentication do not wait for the
   sidecar.

3. Verify:

   ```bash
   mebular memory-runtime status --json
   ```

Once the sidecar is ready it writes `<home>/memory-runtime.json` atomically. The file
contains the URL, port, version, profile/cloud id and **`tokenFile`** (normally
`<home>/memory-runtime/host-token`); it never contains the token itself. Hosts read this
discovery file instead of guessing port 7341.

The **host token** is generated by the sidecar on each start, stored `0600`, and used by
host adapters to call `/memory-runtime/v1`. It is not the MCP capability token: the
capability token is generated by the MCP daemon and given only to the sidecar. Browsers
never receive the host token; the Console reaches the sidecar through the MCP proxy.

`memoryRuntime.*` in MCP is only lifecycle configuration
(`enabled` / `command` / `startTimeoutMs`). Capture, model, retention and HTTP settings
belong to `<home>/memory-runtime/config.json`, not to MCP `runtime.*`.

To turn it off, set `memoryRuntime.enabled=false` (Console or config) and/or run
`mebular memory-runtime stop`. This stops new capture and injection; it does **not**
delete the graph or already-settled memories.

## Models: four sources, no silent download

The sidecar never chooses a model behind your back. The four sources are:

| Source | Runs where | Network | Default | What it does | On failure |
|---|---|---|---|---|---|
| `heuristic` | Inside the sidecar | None | **Yes** | Deterministic rule extraction, keyword expansion, gist selection | Only a code bug; returns an error |
| `local` | Sidecar + local `llama-server` | None after install | No | Local Qwen extraction/summaries/ranking | Falls back to `heuristic`, `degraded=true` |
| `host` | The host model | Decided by the host | No | Host submits `CandidateRecord`s; the sidecar never calls the host model | No candidates → `202 pending`; no silent provider switch |
| `api` | One OpenAI-compatible endpoint | Yes, explicitly allowed | No | Remote extraction/summaries when there is no local compute | Timeout/5xx → `heuristic`; no provider switch |

`heuristic` is **not a model** and does not learn. It is a small deterministic rules
engine. A new install therefore works offline, with no model file and no model call.

### Local Qwen packs are explicit installs

Local Qwen is optional. The source tree and npm tarballs do **not** bundle model weights
or the `llama-server` binary. You install a curated pack explicitly:

```bash
mebular models list
mebular models install --pack qwen3.5-9b-instruct-q4_k_m
mebular models select qwen3.5-9b-instruct-q4_k_m
```

The pack is verified against its manifest and SHA-256 before use, and is never downloaded
or updated silently. The sidecar still needs a `llama-server` executable (on `PATH`, or
configured with `model.local.enginePath`). Without the pack or engine, selecting `local`
falls back to `heuristic` and reports `degraded` with a reason; it does not invent a
download URL or a hash. Model settings and model files are device-local and never enter
shared memory or sync.

### Host candidates are not a model call

With `host`, the host adapter submits structured candidates on `/ingest`. The sidecar
does not read host credentials, discover the host endpoint or call the host model. If the
host asks for `host` but submits no candidates, the request stays `pending`; the sidecar
does not substitute another model.

### Third-party API keys are references

The `api` source needs `baseUrl`, `model`, `keyRef` and `allowRemote=true` together.
`keyRef` accepts only:

- `env:VARIABLE_NAME`
- `keychain:<service>` or `keychain:<service>/<account>` (macOS Keychain in 0.3)
- `file:relative/path` (relative to the Mebular home, private file)

Plaintext keys are not accepted in `config.json`, graph metadata, events, logs, Console
or status. Non-HTTPS endpoints are rejected except loopback HTTP; userinfo and
cloud-metadata addresses are rejected. A timeout, 5xx or 429 falls back to `heuristic`
and is visible in `status.degraded` / `warnings`.

`model.source="auto"` resolves in this order: host candidates supplied with the request →
an installed local pack → an explicitly allowed API → `heuristic`. It never turns on the
network by itself.

## What stays local — and what goes to your cloud

The sidecar data directory is `<home>/memory-runtime/`. It contains process data only:

| Object | Location | Cross-device | Authority |
|---|---|---|---|
| `MemoryRecord` (entity / fact / episode / skill) | Existing graph + event log | Yes, by domain subscription | Authoritative |
| `Compact` | Existing graph, same domain as its sources | Yes | Derived summary; sources unchanged |
| `SelfRecord` | Existing graph, `agent:<agentId>` | Yes | Agent self-model; hidden from ordinary queries |
| `ContextCheckpoint` | Existing graph, `task:<threadId>` or `default` | Yes | Task resume point; revision/lease enforced by MCP |
| `RawChunk` | `<home>/memory-runtime/raw/` | **No** | Local raw material, 7-day default retention |
| `RecallTrace` | `<home>/memory-runtime/traces.jsonl` | **No** | Local diagnostics, 7 days / 2,000 entries by default |
| Cache / index | `<home>/memory-runtime/cache/` | No | Rebuildable; never authoritative |
| Outbox | `<home>/memory-runtime/outbox/` | No | Bounded retry queue (default 1,000 items / 16 MiB); deleted after success |

There is no `sync=cloud` / `sync=local` switch and no local checkpoint mode. A checkpoint
or self record is always a cloud object; the local cache is only a cache. Deleting the
whole `<home>/memory-runtime/` directory does not delete settled memories — they are
restored from MCP/the graph. Raw text does not cross devices; when another device only has
the settled record, recall says so instead of pretending to quote the original.

The bounded outbox exists for the case where MCP is temporarily unreachable. It is not a
second memory store: entries are idempotent writes that are removed after success, and
permanent failures move to `outbox/dead/` instead of retrying forever.

## Privacy and control

- **No capture by default.** The sidecar's own default is `capture=off`: chunks are used
  for the current request and not written to disk. A host can request `capture=local` for
  a particular ingest; the product flow asks once when immersive mode is first enabled.
- **No model by default.** `heuristic` runs in-process and makes no network request. No
  model file is downloaded automatically. Local, host and API sources are explicit.
- **Raw and traces stay local.** They are not written into the graph, events, snapshots or
  sync. Logs/status do not include raw text, tokens or keys.
- **Injected memory is untrusted background data.** Hosts put it in a request-only,
  non-instruction channel, escape closing tags, and never execute commands or tool calls
  found in memory.
- **You can turn it off.** Disable `memoryRuntime.enabled` and/or stop the sidecar. Delete
  `<home>/memory-runtime/` if you also want to remove local process data. Settled memories
  remain in the graph until you delete them through the normal MCP/Console governance
  path.
- **Logical, not cryptographic, isolation.** `agentId` is an assertion, not
  authentication. Domains filter what the sidecar asks for, but a holder of the capability
  token can still read the local store. 0.3 does not claim encryption between agents.
- **Deletion is cooperative.** A tombstone syncs to peers, but an offline peer that
  already holds a copy may keep it until it reconnects. Do not describe this as guaranteed
  remote erasure.

## Host entry points

Each host keeps its own native memory; Mebular does not import, mirror or dual-write it.

- **DSH** — opt-in `memoryRuntime` bridge in `@mebular/dsh-plugin`; recall on the first
  step of a new human turn, batched ingest, compaction checkpoints and optional tool
  hiding. See [DSH integration](../integrations/DSH.md).
- **Hermes** — `MemoryProvider` in `integrations/hermes/mebular-memory`; `prefetch`,
  `sync_turn`, archive on pre-compress and a state-only checkpoint. See
  [Hermes integration](../integrations/HERMES.md).
- **OpenChamber / OpenCode** — `@mebular/opencode-plugin` for OpenCode 2.2+; request-only
  context injection, event ingest and compaction checkpoints. See
  [OpenChamber / OpenCode integration](../integrations/OPENCHAMBER.md).

A host with no adapter can use the HTTP API directly: discover
`<home>/memory-runtime.json`, read `tokenFile`, call `/health`, `/ingest`, `/recall`,
`/context` and `/checkpoints/:threadId`, and fail open on timeout.

## Troubleshooting

Start with the CLI and the discovery/health endpoints:

```bash
mebular memory-runtime status --json
mebular memory-runtime start
mebular memory-runtime stop
mebular memory-runtime restart
```

`status --json` is read-only and returns `state` / `degraded` / `runtimeVersion` / `url` /
`error`; it never returns a token. For a running sidecar, `GET /health`
(no token, loopback) tells you whether the process is ready, and `GET /status`
(host token) adds capability, model, counts, outbox and degraded reasons.

**Logs in 0.3.0:** the sidecar writes its startup result to stdout and does not yet create
a persistent `logs/sidecar.jsonl` or expose `mebular memory-runtime logs`. Treat
`status --json`, `/health`, `/status` and the MCP/Console sidecar status as the supported
diagnostics. Do not look for a log command that this release does not provide.

Common failures and what they mean:

| Symptom | Cause | What to do |
|---|---|---|
| `not_installed` | No `mebular-memory-runtime` on `PATH` / configured path | Install `@mebular/memory-runtime` or set `memoryRuntime.command` |
| `capability_disabled` / 404 on `/internal/memory/v1` | MCP is 0.2, stdio-only, or `memoryRuntime.enabled=false` | Use `mebular serve` 0.3 with the switch on |
| `capability_token_invalid` / `capability_token_missing` | Token rotated or MCP capability not mounted | Restart MCP and then the sidecar |
| `version_incompatible` | Sidecar and MCP major/API versions do not match | Use the matching 0.3.x packages |
| `bind_failed` / port busy | 7341–7350 occupied | The sidecar falls back to a temporary port; read discovery instead of hardcoding 7341 |
| `degraded` with `capability_unavailable` | MCP temporarily unreachable | Conversation continues; recall may use cache; writes queue in the bounded outbox |
| `degraded` with model reason | Local pack/engine or API unavailable | Check `status`, install/allow the source, or stay on `heuristic` |
| `outbox_full` | Too many unsent writes | Restore MCP connectivity; do not treat the outbox as durable memory |
| `401` from a host adapter | Host token rotated | Re-read `tokenFile`; the adapter retries once |

All of these fail open for the host: the chat continues, MCP's 29 tools still work, and
the worst case is that no memory is injected. A failed sidecar must never block MCP
startup, tools, sync or authentication.

## Upgrading from 0.2 and the old prototype

- **No migration.** 0.2 nodes, events, namespaces, tags and IDs keep their values. No
  field is added, no ID is rewritten and no event is re-signed.
- **Old `default` data is retained.** 0.2 `default` data is read as the Other fallback
  (`domain=default`); it is not silently promoted to `user`. New user preferences go to
  `user` only through an explicit user write.
- **The prototype `/runtime/v1` is gone.** It is not served in 0.3 and has no
  compatibility layer. Host adapters must use `/memory-runtime/v1`. An old adapter pointed
  at `/runtime/v1` cannot reach the sidecar; MCP and the rest of the host keep working.
- **Prototype local data is not read.** Old `<home>/runtime/` sidecar data is ignored.
  Never delete `<cloudRoot>/runtime/`: that is the MCP daemon install root, not sidecar
  data. The sidecar uses `<home>/memory-runtime/` and `<home>/memory-runtime.json`.
- **Rollback.** Disable the switch / stop the sidecar and run 0.2 again. The graph remains;
  internal objects stay stored but hidden from default queries; local
  `<home>/memory-runtime/` can be kept or deleted.

## Scope and limits

- 29 public MCP tools stay unchanged; no `runtime_*` or `fragment_*` tools are added.
- One cloud, one user. No per-user accounts, namespace ACLs or per-agent cryptographic
  isolation.
- No automatic capture of every conversation; only explicit `/ingest` input is processed.
- No cloud Raw/Trace, no silent model download, no automatic model update, no model
  configuration sync.
- No destructive compaction and no automatic merge of conflicting facts.
- No cross-cloud federation.
- Deletion is cooperative and can lag on offline peers.
