# Fleet 黑盒编排演示：A 如何完成一个真实请求

> 目的：用一个可运行的场景说明本期改动合入后，用户对 A 说一句话，Fleet 内部实际会发生什么。
> 这不是新的协议或接口；它复用现有的 `task_submit.plan`、plan materializer、capability routing、join 和 MR 门禁。

## 场景

用户只对设备 A 上的 Agent 说：

> “把 X 模块重构、补测试、更新文档，最后提个 MR。”

A 不需要用户打开 Fleet 页面、配置卡片或手动拆任务。它提交一个内部 plan：

| step | 工作 | 目标 | 依赖 |
|---|---|---|---|
| `code` | 重构 X 模块 | 有 `code.write` 能力的设备 | — |
| `tests` | 补齐测试 | 有 `test` 能力的设备 | — |
| `docs` | 更新文档 | 有 `docs` 能力的设备 | — |
| `gate` | 全量汇合 | J | code/tests/docs |
| `mr` | 提交一次 MR | plan owner A | gate |

Fleet 根据能力卡、授权、在线/容量和确定性 tie-break 选择执行者；`gate` 使用 `join.mode="all"`，任何分支失败都不会提前创建 MR。

## 复跑方式

```bash
npm run build
node scripts/fleet-blackbox-demo.mjs
```

演示使用真实 Fleet plan/materializer/routing/join/MR 代码，网络层使用进程内 `InMemoryHub` 隔离调度抖动；执行器使用 `EchoExecutor` 模拟工作结果，不修改真实仓库。该边界与 P6 五节点 E2E 相同。

## 实际输出（2026-11-05，当前分支）

```text
用户 → A: “把 X 模块重构、补测试、更新文档，最后提个 MR。”
A → Fleet: task_submit.plan  planId=plan-demo-blackbox-001 version=1
Fleet → A: rootTaskId=plan-demo-blackbox-001#1#root

A 的计划（内部可见，人类 UI 不显示）:
  step   status    chosen                 why
  code  done      -> device-B/worker        why=ASSIGNED
  tests done      -> device-C/worker        why=ASSIGNED
  docs  done      -> device-D/worker        why=ASSIGNED
  gate  done      -> device-J/worker        why=ASSIGNED
  mr    done      -> device-A/planner       why=done

实际执行结果:
  plan status: done
  root status: done
  MR created: 1（跨版本引用 1）
  task_status.plan: readable

用户看到的结果: 任务完成；MR 只提交一次；没有打开 plan 页面或配置卡片。
```

## 这个输出证明了什么

- **A 只调用现有工具**：`task_submit.plan` 返回 `planId` / `rootTaskId`，没有新增 `plan_*` 或 `agent_card_*` MCP 方法。
- **按能力路由**：B/C/D 分别拿到 code/test/docs 分支；J 承担全量 gate；A 作为 plan owner 执行最终 MR。
- **join 与 MR 门禁生效**：`gate` 依赖全部完成，MR 只创建一次，root 在 MR 后完成。
- **用户侧零新增入口**：plan/step 进度只通过内部 `task_status.plan` 可读；人类 Console 没有 Fleet 页面、导航或卡片配置。
- **可解释**：每个 step 的 `why=ASSIGNED` 来自 route 解释；实际执行时 target 与 chosen 一致。

## 边界

- 该演示使用 `InMemoryHub`，不是真实 3+ 节点 libp2p 或 WAN 性能证据；真实网络证据仍是 `verify:fleet:tasks`（2 节点）与 `verify:daemon:cluster`（双守护 2 节点）。
- `EchoExecutor` 只模拟成功执行；分支失败、v2 `reuse` 重试、cancel 和 MR 不提前提交由 `verify:fleet:p6` / `tests/fleet/join-mr.test.ts` 覆盖。
- DSH/OpenCode/Claude Code 的真实宿主 smoke 仍按 `docs/quality/0.3.2-fleet-orchestration.md` 的边界执行；本演示不把 fake CLI 当作真实宿主 E2E。
