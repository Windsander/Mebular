## 1. 结论摘要

1. 1k smoke 在真实 MCP capability、真实 `GraphStore`/`MemoryService`、真实 managed sidecar 上通过：图内精确得到 **1,000 条 MemoryRecord + 1,000 条 Detail**，staging/outbox/dead 均为 0，临时 home 与 sidecar 进程均清理成功。
2. 1k 写入吞吐约 **7.7–9.4 records/s**；每批次 50 条的端到端 ingest p50 约 **5.0–6.0 s**、p95 约 **7.3–9.7 s**，折合每条 p50 约 **99–121 ms**。写入延迟包含 sidecar 串行 ingest、capability `/write`、`/detail`、每条 Detail 的权威回读、缓存写入和 staging 清理，不能单独归因于 GraphStore。
3. 1k 读取 p50：capability `/query` **5.5–5.7 ms**、sidecar `/recall` **43.4–50.1 ms**、sidecar `/context` **43.3–44.8 ms**、`/recall/:id/expand` **7.2 ms**（90 次可展开样本）。四类读取的 marker 命中率均为 100%（在可发起展开的样本内）。
4. **发现一个 WP1 详情证据关联缺口（P1）：** 按 detail-kind 分层的 100 个读取样本中，**conversation 90/90 可展开，但 tool_output 0/6、document_slice 0/4 可展开**，整体可展开覆盖率 90%。根因是 `recall.resolveDetailIds()` 只查询 `detailKinds: ['raw_chunk']`，而 WP1 已允许 `tool_output` 与 `document_slice`。该问题不改变图内 Detail 数量，但会让部分召回碎片“有 Detail 却无法展开”。本基准不修改产品，详见 §6.2。
5. 资源侧：1k 后 `device.jsonl` 约 **16.2 MB**（约 16 KB/条记录+详情），sidecar RSS 约 **152–164 MB**（基线约 83–86 MB），detail cache 1,000 条约 1.28 MB，幂等账本约 0.6 MB；outbox/dead 为 0。
6. **10k full 未完成。** 本机跑到 2,000/10,000 时约 8–9 分钟；按 1k→2k 的成本增长外推，10k 约需 3–4 小时，超出合理单次基准时间，已中止且未生成 10k JSON。10k 仍需在性能修复后或专用长跑窗口复测；不能把 1k 数字外推成 10k 结果。

## 3. 数据集与工作负载

- **数据形状：** 每个逻辑项 = 1 个 raw chunk + 1 个 host candidate → 1 条 MemoryRecord + 1 条 Detail。
- **detail-kind 分布（按索引模 100 固定）：**
  - 80% `user` / `raw_chunk`（conversation）
  - 10% `assistant` / `raw_chunk`（conversation）
  - 6% `tool` / `tool_output`
  - 4% `user` / `document_slice`
- **内容：** 合成 marker + 固定说明文本，约 220–260 bytes/条；无真实用户内容、token、密钥或真实 home 路径。
- **写入路径：** 通过真实 sidecar `POST /ingest`，不是直接调用 `MemoryService.write()`；因此覆盖 staging → capability `/write` → capability `/detail` → 权威 `detail get` → sidecar detail cache → staging 清理。
- **批次：** 1k smoke `--batch-size 50`；10k full `--batch-size 100`（sidecar/capability 上限 100）。
- **读取采样：** 按 `index % 100` 的 detail-kind 桶分层，使每类 detail-kind 都进入样本；1k 采 100 个、10k 采 200 个。查询文本为唯一 marker（含 4 位数字片段，触发 recall 的 exact/expand 意图）。
- **延迟定义：** 每次 await 的端到端墙钟时间；分位数为 nearest-rank（`ceil(p*n)-1`）。写入吞吐 = 逻辑 records / 总写入墙钟时间，不是单条并发吞吐。
- **RSS：** 宿主进程用 `process.memoryUsage().rss`；sidecar 用 `ps -o rss=` 读取子进程 RSS（KB → bytes）。
- **磁盘：** 逻辑字节为递归 `stat`，另有 `du -sk` 的分配字节。

## 6. 发现与建议

### 6.1 写入吞吐与单条成本

- 1k 的端到端 ingest p50 约 5.0–6.0 s/50 条，折合 99–121 ms/条；写入吞吐 7.7–9.4 条/s。
- 这条链路包含：sidecar 串行 ingest 锁、staging 写入与校验、capability `/write` 逐条图写入、capability `/detail` 批量写入、**每条 Detail 的权威回读**、detail cache 写入、staging 清理、幂等响应账本持久化。
- 因此该数字是“真实用户路径吞吐”，不是纯 GraphStore 写入吞吐。若需要定位到单组件，建议 WP6 后续增加 capability `/write` 与 `/detail` 的独立微基准；本会话不修改产品代码。
- 风险：10k 全量预计需要约 18–25 分钟（1k 的 10 倍加数据增长），不适合接入普通 PR CI；应作为手动/ nightly 规模门禁，或降低到 1k smoke 作 PR 证据、10k 作发布前证据。

### 6.2 Detail 展开覆盖缺口（P1，建议在 WP1/Recall 修复）

**现象：** 图内 1,000 条 Detail 全部存在（`counts.details=1000`），但召回读取样本中 `tool_output` 与 `document_slice` 的碎片没有 `detailIds`，导致 `/recall/:id/expand` 无法发起；conversation 两类均 100% 可展开。

**根因：** `packages/memory-runtime/src/sidecar/recall.ts` 的 `resolveDetailIds()` 在记录没有前向 `detailIds` 时，向 capability `/detail op=list` 传入固定 `detailKinds: ['raw_chunk']`。而 WP1 已把 `tool_output`、`document_slice` 作为合法 DetailKind 写入；capability 也不会在 MemoryRecord 上保留前向 `provenance.detailIds`（契约 §2.3）。于是 recall 只找到 raw_chunk，非 raw_chunk 的详情永远不会被关联到召回碎片。

**影响：**

- 召回碎片会出现 `hasDetail=true` 但 `detailIds=[]`、`detailAvailable=false`、`detailAvailability=['pending_sync']`；`/expand` 只能返回 `detail=null` + `detail_pending_sync`，把“未关联”误报成“同步中”，用户无法看到工具输出/文档切片原文。
- 不影响图内 Detail 数量和 retention 元数据；不影响 conversation 路径。
- 这属于 WP1 数据路径/C03 详情证据关联的验收 blocker，不应以“规模基准通过”掩盖。

**建议（不修改产品，仅建议）：**

1. `resolveDetailIds()` 查询 canonical detail kind 集合（`raw_chunk`、`message`、`tool_output`、`document_slice`），或省略 `detailKinds` 过滤，由 capability 做域/记录/保留校验；保持最多 3 条和现有配额。
2. 增加回归测试：分别写入 conversation、tool_output、document_slice 各一条 Detail，召回后断言 `detailIds` 非空且 `/expand` 返回对应原文。
3. 修复后重跑本基准的 1k/10k，确认 `detailCoverage.coverageRate` 从 90% 提升到 100%，且 `tool_output`/`document_slice` 分项为 100%。

### 6.3 磁盘与内存

- `device.jsonl` 在 1k 时约 16.2 MB，约 **16 KB/条记录+详情**；事件日志保留完整 create/update 节点版本是契约已披露行为，不是泄漏，但 10k 时需要关注磁盘增长。
- detail cache 在 1k 时为 1,000 条 / 1.28 MB；10k 时会受 5,000 条 / 256 MiB 上限约束，需以 10k JSON 的 `detailCacheEntries` 为准。
- 幂等账本在 40 个 ingest 批次后为 0.60 MB；每个批次响应包含 50–100 条记录/详情结果，账本会保留完整响应视图。10k 时账本上限 5,000 条，需以 JSON 为准。
- 1k 后 sidecar RSS 增加约 76–78 MB、宿主 RSS 增加约 14–85 MB（宿主数值受 V8 GC 影响明显）；这是含 Node/V8 堆、图索引和缓存的总量，不是纯数据大小。10k 数值见下一节。

## 7. 10k full 尝试结果（未完成，不计为通过）

**结论：** 在本机（Intel i7-8850H / 32 GiB / Node 26 / 当前 SHA）无法在合理时间内完成 10k full。运行到 **2,000/10,000** 时已耗时约 **8–9 分钟**，据此中止；未生成 `docs/quality/0.3.2-scale-benchmark-10k.json`，也不以 1k 数据外推填充 10k 表格。

| 中止时观测项 | 值 |
|---|---:|
| 已完成记录 / 详情 | 2,000 / 2,000（20/100 批次） |
| 已耗时 | 约 8–9 分钟 |
| 折算吞吐 | 约 3.7–4.1 records/s |
| 宿主进程 RSS | 183.2 MB |
| sidecar RSS | 172.7 MB |
| 临时 home 磁盘 | 57 MB（`du -sh`） |
| `device.jsonl` | 42 MB / 32,400 行 |
| 幂等账本 | 1.5 MB |
| 清理 | 手动中止后已停止 sidecar、删除临时 home |

**为什么判定不合理：** 1k 时写入成本约 0.13 s/条；2k 时约 0.25–0.27 s/条，成本随数据量明显上升。即使按线性增长保守外推，10k 也需约 3–4 小时；若继续增长则更久。这不是“等一会儿就好”的噪声，而是需要在性能修复后复测的规模问题。

**后续运行要求：**

1. 先定位写入路径的数据规模依赖。代码审查给出的优先怀疑点（尚未通过固定 batch 阶梯证实）：capability `buildDedupeIndex()` 每批全量扫描节点；`MemoryService.writeDetailsLocked()` 每批 `detailNodes()` 全量扫描；`ensureDetailQuota()` 对 `live` 数组逐项做 O(n) 域/云用量计算；以及事件日志每个逻辑对象追加多条含完整节点版本的记录（100 条记录+详情产生 1,200 行 / 1.5 MB，约 15 KB/逻辑项）。先做固定 batch 的 1k/2k/4k 阶梯和 capability `/write`、`/detail` 分项计时，再决定修复或接受长跑。
2. 修复后在**干净 SHA** 上运行 §8 的 10k 命令，保存 `docs/quality/0.3.2-scale-benchmark-10k.json`。
3. 若最终决定不修复，由 chief/用户显式接受“10k 规模证据缺失”，并把 C19 的规模声明收窄；不得用 1k 结果替代。

## 8. 复现命令

```bash
# 先构建 dist（基准脚本复用真实 MCP/capability 与 sidecar 入口）
npm ci
npm run build

# 1k smoke：约 2 分钟（本机）
node tests/integration/scale-bench/run.mjs \
  --records 1000 --details 1000 --batch-size 50 --queries 100 \
  --label 1k-smoke \
  --output docs/quality/0.3.2-scale-benchmark.json

# 10k full：本机实测跑到 2k/10k 已约 8–9 分钟，外推 3–4 小时；
# 必须在性能修复后或专用长跑窗口单独运行，不要与其他基准并行
node tests/integration/scale-bench/run.mjs \
  --records 10000 --details 10000 --batch-size 100 --queries 200 \
  --label 10k-full \
  --output docs/quality/0.3.2-scale-benchmark-10k.json
```

- 脚本不接受 `--records` 与 `--details` 不相等：每个 ingest 项固定产生 1 条记录 + 1 条详情，避免“用少写详情冒充 10k Detail”。
- 默认输出路径为 `docs/quality/0.3.2-scale-benchmark.json`；可用 `--output` 指定。
- `--keep` 可保留临时 home 排障；默认在 `finally` 中删除，并确认 managed sidecar 进程停止。
- 不接入 CI；最终由 chief 决定 nightly/release 门禁位置。

## 9. 限制与风险

1. **不是宿主/模型证据。** 没有真实 DSH/Hermes/OpenCode/OpenChamber 进程、真实模型、P2P 对端或 Console UI；不能用于 C19 的宿主注入、模型 canary、Recall@k 质量或升级/回滚声明。
2. **查询是合成 marker。** 每条查询都精确包含唯一 marker，命中率高不代表自然语言召回质量；`recall@k`、遗漏率、误召回轮次率需由质量基准单独测量。
3. **单机单次。** 绝对值依赖 Intel i7-8850H、Node 26、macOS 和当时负载；不应把 p95 当作跨平台 SLA。1k 两次写入墙钟差异约 21%，已说明本机噪声。
4. **小样本分位数。** 1k/100 样本、10k/200 样本的 p99 实际接近 max，nearest-rank 分位数较粗；报告同时给出 max。
5. **10k 运行成本高且本机未完成。** 2k/10k 已耗时约 8–9 分钟，外推 3–4 小时；期间生成数十至百 MB 级临时图/事件日志。已中止并清理，未把 2k 观测写成 10k 结果。不要在用户真实 home 或共享 CI runner 上无约束运行。
6. **已存在的 P1 详情覆盖缺口。** 见 §6.2；修复前不应宣称“所有 detail-kind 均可展开”。本会话按授权不修改产品代码。
7. **缓存与账本上限尚未在 10k 验证。** 1k 未触及 detail cache / capability 幂等账本的 5,000 条上限；10k 是否触及以及实际规模需以未来 10k JSON 的 `detailCacheEntries`、`idempotencyLedgerEntries` 为准，不能凭请求数推断。
