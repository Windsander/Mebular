## 3. 数据集与工作负载

- **数据形状：** 每个逻辑项 = 1 个 raw chunk + 1 个 host candidate → 1 条 MemoryRecord + 1 条 Detail。
- **detail-kind 分布（按索引模 100 固定）：**
  - 80% `user` / `raw_chunk`（conversation）
  - 10% `assistant` / `raw_chunk`（conversation）
  - 6% `tool` / `tool_output`
  - 4% `user` / `document_slice`
- **内容：** 合成 marker + 固定说明文本，约 220–260 bytes/条；无真实用户内容、token、密钥或真实 home 路径。
- **写入路径：** 通过真实 sidecar `POST /ingest`，不是直接调用 `MemoryService.write()`；因此覆盖 staging → capability `/write` → capability `/detail` → 权威 `detail get` → sidecar detail cache → staging 清理。
- **批次：** 1k `--batch-size 50`；2k/10k `--batch-size 100`（sidecar/capability 上限 100）。
- **读取采样：** 按 `index % 100` 的 detail-kind 桶分层；1k/2k 采 100 个，10k 计划 200 个。查询文本为唯一 marker（含 4 位数字片段，触发 recall 的 exact/expand 意图）。
- **存储断言：** 写入后按 index 0/80/90/96 取 4 个探针，先经 capability `/query` 找到对应 MemoryRecord，再用 capability `/detail op=list` + `recordIds` 读取，断言 `detailKind` 分别为 `raw_chunk`（两类 conversation）、`tool_output`、`document_slice`。
- **计数审计（本轮新增）：** seed 响应中的每个 record ID 都进入内存集合；seed 后经 capability `/query` 分页读取所有非保留域（`includeHistory=true`、`includeArchived=true`），验证：
  1. 写入响应 ID 数量/去重数量等于请求 records；
  2. 每个种子 ID 在图中存在，且带 `scale-bench` tag；
  3. 所有非种子 MemoryRecord 单独按 domain/type/kind/tags/provenance 分组输出，检测其正文是否与种子重复；
  4. `status.counts.details` 必须精确等于请求 details。
  审计不是把 `memoryRecords >= records` 当通过；`--allow-extra-records` 仅用于生成完整诊断 JSON，若 extras 与种子正文重复，最终 status 仍强制为 `failed`。
- **规模化保护：** 默认 `--max-records 2000`、`--max-queries 500`；超过默认值必须显式 `--allow-large`，硬上限 100,000 records / 2,000 queries。整体默认超时 30 分钟，单请求默认 120 秒；启动前做磁盘/可用内存预检。
- **延迟定义：** 每次 await 的端到端墙钟时间；分位数为 nearest-rank（`ceil(p*n)-1`）。写入吞吐 = 逻辑 records / 总写入墙钟时间，不是单条并发吞吐。
- **RSS：** 宿主进程用 `process.memoryUsage().rss`；sidecar 用 `ps -o rss=` 读取子进程 RSS（KB → bytes）。
- **磁盘：** 逻辑字节为递归 `stat`，另有 `du -sk` 的分配字节。

## 5. 计数审计修复与 1k/2k 验证

### 5.1 为什么不能直接用 `memoryRecords === records` 作为唯一断言

旧脚本只比较 capability `/status` 的全局 `counts.memoryRecords` 与请求 records。这个计数包含所有非保留域的普通 MemoryRecord，但无法区分：

- 来自别的 domain/历史/非种子节点的记录；
- 产品路径重复写出的同正文记录；
- 一个批次部分提交后在重试中再次提交的尾部记录。

因此本轮把断言拆成两层：

1. **种子完整性：** 10,000 个写入响应 ID 是否全部、唯一、带 tag 地存在；
2. **额外记录透明化：** 任何非种子记录都进入 `countAudit.extras`，按 domain/type/kind/tags/provenance 分组；若正文与种子重复，直接判定产品重复写入并非通过。

## 6. 10k 失败与 23 条额外记录根因

### 6.1 原始 10k 失败 run（SHA 7386495，干净工作区）

| 指标 | 实测 |
|---|---:|
| 请求 records / details | 10,000 / 10,000 |
| 写入响应 records / details | 10,000 / 10,000 |
| 完成批次 | 100 / 100 |
| seed 墙钟 | 5,241.9 s（87.4 min） |
| seed 吞吐 | 1.91 records/s |
| 批次延迟 p50 / p95 / p99 / max | 53.28 / 105.21 / 157.56 / 160.43 s |
| capability `/status` memoryRecords | **10,023** |
| capability `/status` details | 10,000 |
| 读取 | 未开始（严格计数在读取前失败） |
| cleanup | `cleaned=true`，`tempHomeRemoved=true`，`residualPids=[]` |
| 错误 | `量级校验失败：期望 10000 records/10000 details，实际 10023 records/10000 details` |
| 机器可读证据 | `0.3.2-scale-benchmark-10k.json` |

### 6.2 根因链

1. **sidecar 对 capability 的默认超时是 5s，且 mutating 请求会重试。**
   `packages/memory-runtime/src/sidecar/config.ts` 的默认 `capability.timeoutMs=5000`；`CapabilityClient.call()` 在 timeout/retryable 错误时使用**同一个请求体、同一个 `Idempotency-Key`** 重试（默认 `retries=2`，最多 3 次）。
2. **10k 的写入路径在高位已经明显超过单次 5s 预算。**
   原始 10k 的 batch 89–100 达到 103–160 s/批；写入链路含 capability 全图去重索引、逐条 `writeRecords`、tag/metadata 更新、detail 批次与权威回读。高负载下单个能力请求超过 5s 后，sidecar 会启动重试，而原请求仍在服务端继续执行。
3. **capability 幂等层没有 in-flight 去重/租约。**
   `withIdempotency()` 只在请求开始读 ledger、请求结束写 ledger；同一 composite key 的两个并发请求都可能看到 “不存在”，然后各自执行。受控探针用两个并发 `/write`（同一 key、同一 100 个 item）得到两个 `created=100, replayed=false`，图内 **200 records**。
4. **重试在中间快照上重建去重索引，原请求的尾部继续落图。**
   `handleWrite()` 在每个请求开始时 `buildDedupeIndex()` 全量扫描；重试看到的只是原请求当时的中间状态。重试创建了原请求尚未写入的尾部 item；原请求随后又写了一遍这些 item。seed 响应返回重试的 100 个 ID，原请求尾部成为 **非种子重复记录**。
5. **details 精确保持 10,000 的原因。**
   Detail 写入使用 seed 响应返回的 record ID 关联；重复的原请求尾部没有进入响应集合，因此没有额外 Detail。于是出现 10k 特有的 **records 多、details 正好相等** 签名。

### 6.3 受控复现证据（修复前，`19cac09`）

`tests/integration/scale-bench/race-probe.mjs` 在最终 SHA `19cac09`、干净工作区上运行，真实组件与基准一致，只控制并发/超时：

| 探针 | 逻辑 records | 图中 records | 图中 details | 关键响应 |
|---|---:|---:|---:|---|
| 同一幂等键两路并发 `/write` | 100 | **200** | 0 | 两路都 `created=100, duplicates=0, replayed=false` |
| 真实 sidecar `/ingest`，`capability.timeoutMs=200ms` | 100 | **131** | **100** | `recordsReturned=100`，`detailsReturned=100`，warnings=[] |

第二行与 10k 的 `records=10023, details=10000` 是同一签名：records 因 timeout/retry 竞争多出，details 只按响应 ID 关联而保持精确。200ms 是**受控放大**（默认 5s），用于在小数据量下稳定复现，不是 10k 实际配置；10k 实际使用默认 5s。以上保留为修复前历史证据；修复后同一探针结果见 §6.4。

### 6.4 判定与修复状态（`ca2193e`）

- **这是产品意外写入，不是 benchmark 计数口径。** 23 条不是历史/非种子治理节点，也不是 stats 把内部对象算进 records；而是同一逻辑 item 的两条不同 ID 记录。
- **原始 10k 失败证据保留，10k 仍不通过。** SHA `7386495` 的 `10,023 records / 10,000 details` 是历史失败事实；不得把断言改成 `>=`、不得按 tag 过滤掉 extras、不得把 1k/2k/6k 外推成 10k 通过。`ca2193e` 尚未重跑完整 10k，因此本轮不得声明 10k 通过。
- **根因已由 `ca2193e` 单飞修复。** `withIdempotency()` 现在按 composite key `(tokenId, route, Idempotency-Key)` 维护 in-flight Map：并发同 key + 同 body hash 只执行一次，另一路等待同一 Promise 并得到等价结果；同 key + 不同 body hash 立即 `409 idempotency_conflict`；execute 失败时在 `finally` 清理，后续可重试；成功结果仍按既有规则写 ledger，`partial/failed` 仍不缓存。新增了 join + close/drain 回归，确认 close 等待两路在途请求并按既有语义 clean 撤销。
- **修复后受控证据（`docs/quality/0.3.2-scale-benchmark-race-probe.json`，SHA `ca2193e`，干净工作区）：**

| 探针 | 逻辑 records | 图中 records | 图中 details | 结果 |
|---|---:|---:|---:|---|
| 同一幂等键两路并发 `/write` | 100 | **100** | 0 | `not-reproduced`，两路同一组 result IDs，`duplicated=0` |
| 真实 sidecar `/ingest`，`capability.timeoutMs=200ms` | 100 | **100** | **100** | `not-reproduced`，`duplicated=0`，不再出现 10k 的 records>details 签名 |

- **sidecar timeout/retry 未在本次修复中修改。** 5s 默认超时与重试策略仍按原实现；单飞只保证同一幂等键的并发重试不会重复落图。完整 10k 重跑与最终性能/延迟验收仍是后续 blocker。

## 7. 失败 / 中断路径证据

`tests/integration/scale-bench/failure-injection.mjs` 在最终 SHA `19cac09` 上重跑，6 个场景全部通过；使用同一真实 cluster，仅控制失败时机。

| 场景 | 退出码 | 结果 | 关键证据 | 清理 |
|---|---:|---|---|---|
| seed 注入失败 | 1 | `failed` | 写入 5 条 / 1 批次后抛错；5 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| read 注入失败 | 1 | `failed` | seed 完成 20/20；reads 完成 1 个样本后抛错；14 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| SIGTERM 中断 | 143 | `interrupted` | 已完成 20 条 / 2 批次；8 次 checkpoint；partial JSON 保留 | `cleaned=true`，`residualPids=[]` |
| SIGINT 中断 | 130 | `interrupted` | 已完成 20 条 / 2 批次；8 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| sidecar SIGKILL | 0（重启后跑完） | `passed` | kill 于第 1 批次，pid `84445`；重启 pid `84460` 被 tracker 记录；最终 20/20、reads 2/2 | `cleaned=true`，`residualPids=[]` |
| 冻结 sidecar + 清理升级 | 1 | `failed` | `sidecar_sigstop` 冻结；清理 SIGTERM 5s 未退出后 SIGKILL；`escalation=SIGKILL` | `cleaned=true`，`tempHomeRemoved=true`，`residualPids=[]` |

实现要点：

- **partial JSON：** 每批次、每 5 个 read 样本、进入失败/中断、cleanup 前后都会原子写入 `<output>.tmp-* → rename`；最终 JSON 也走同一路径。
- **SIGINT/SIGTERM：** 第一次信号请求停止，循环在安全点抛 `AbortError` 并写 partial JSON；20 秒内未完成则 emergency sync 落盘并 SIGKILL tracked sidecar，退出码 130/143。
- **超时：** 整体 `--timeout-ms`（默认 30 分钟）按同一停止路径处理，退出码 124；单请求 `--request-timeout-ms` 默认 120 秒。
- **SIGKILL fallback：** 清理先停 tracked sidecar；SIGTERM 5 秒未退出则 SIGKILL，再由 `ps -axo` 扫描 `--parent-pid <本进程>` 的残留并复检。
- **tempHomeRemoved：** 清理后真实 `stat` 检查路径，存在则重试 `rm` 并暴露非 ENOENT 错误。
- **PID 跟踪：** `cluster-start`、每个 checkpoint、故障注入前都会刷新 discovery pid；tracker 保留历史 PID 和事件，重启后的新 PID 会被记录并在 cleanup 中逐一停止。

## 8. 资源、缓存与账本

- 1k 写入后 `device.jsonl` 约 **16.19 MB**，2k 约 **32.41 MB**；约 16 KB/条记录+详情。事件日志保留完整 create/update 节点版本是契约已披露行为。
- detail cache：1k 为 1,000 条 / 1.28 MB；2k 为 2,000 条 / 2.57 MB。10k 预计触及 **5,000 条 / 256 MiB** 上限，但 10k 未完成读取，最终条目数未验证；不能把 1k/2k 线性外推成 10k。
- 幂等账本：1k/2k 均为 20 个 ingest 批次 → **40 条**（每批次 2 条：`/write` 与 `/detail` 响应）。10k 若按 100 批次预计约 200 条，远低于 5,000 条上限；但 10k 失败 JSON 未包含 afterSeed 资源快照，不能声明已验证。
- 1k/2k sidecar RSS 约 157–180 MB；宿主 RSS 约 143–227 MB（V8 GC 波动明显）。这些是含 Node/V8 堆、图索引和缓存的总量，不是纯数据大小。
- 10k 原始失败 run 的 preflight：free disk 约 323.6 GB、free memory 约 14.58 GB；失败发生在读取前，afterSeed 资源快照未生成，因此不报告 10k RSS/磁盘实测。
- 所有 1k/2k/探针 run 的 staging/outbox/dead 均为 0，cleanup 无残留。

  --label 2k-audit \

  --allow-large --max-records 10000 \

  --allow-large --max-records 10000 --allow-extra-records --audit-every-batches 10 \

  --output /path/to/10k-audit.json

- 脚本不接受 `--records` 与 `--details` 不相等：每个 ingest 项固定产生 1 条记录 + 1 条详情，避免“用少写详情冒充 10k Detail”。

- `--allow-extra-records` 只用于诊断：JSON 会单独报告 extras；若 extras 与种子正文重复，最终 status 仍强制 `failed`。
- 失败注入参数（仅证据使用）：`--fail-after-batches`、`--fail-after-read-samples`、`--kill-sidecar-after-batches`、`--freeze-sidecar-after-batches`。
- 不接入 CI；最终由 chief 决定 nightly/release 门禁位置。

## 10. 限制与风险

1. **10k 未真通过；根因已修复但尚未重跑。** 23 条额外记录来自 capability 幂等并发/超时重试重复写；`ca2193e` 已用 in-flight 单飞修复，但完整 10k 未在该 SHA 上重跑，不能把 10k 标记为通过。
2. **10k 读取指标缺失。** 原始失败 run 在读取前停止；第二次 10k 尝试因宿主超时在 batch 33 停止。不能把 1k/2k/6k 的读取 p50/p95 外推成 10k 结果。
3. **本机不是空闲独立机。** 本轮 1k/2k/探针时存在其它 Hermes/系统负载，第二轮 10k 遇到 load average 约 19；绝对吞吐只代表当时环境。
4. **不是宿主/模型证据。** 没有真实 DSH/Hermes/OpenCode/OpenChamber 进程、真实模型、P2P 对端或 Console UI；不能用于 C19 的宿主注入、模型 canary、Recall@k 质量或升级/回滚声明。
5. **查询是合成 marker。** 每条查询都精确包含唯一 marker，命中率高不代表自然语言召回质量；`recall@k`、遗漏率、误召回轮次率需由质量基准单独测量。
6. **小样本分位数。** 1k/2k/100 样本的 p99 实际接近 max，nearest-rank 分位数较粗；报告同时给出 max。
7. **Detail 覆盖结论只到 1k/2k。** 最终 SHA 的 1k/2k 覆盖为 100%，但 10k 读取未运行，不能声明 10k 所有 detail-kind 可展开。
8. **缓存与账本上限尚未在 10k 验证。** 1k/2k 未触及 detail cache 的 5,000 条上限；10k 最终条目数需在 `ca2193e` 修复后重跑确认。
9. **构建绑定证明的是元数据一致，不是可复现构建。** `version.json` 的 sha 与 HEAD 一致、dist 文件哈希已记录；同一 SHA 重新构建的字节级可复现性未验证。
