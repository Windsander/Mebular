## 3. 数据集与工作负载

- **数据形状：** 每个逻辑项 = 1 个 raw chunk + 1 个 host candidate → 1 条 MemoryRecord + 1 条 Detail。
- **detail-kind 分布（按索引模 100 固定）：**
  - 80% `user` / `raw_chunk`（conversation）
  - 10% `assistant` / `raw_chunk`（conversation）
  - 6% `tool` / `tool_output`
  - 4% `user` / `document_slice`
- **内容：** 合成 marker + 固定说明文本，约 220–260 bytes/条；无真实用户内容、token、密钥或真实 home 路径。
- **写入路径：** 通过真实 sidecar `POST /ingest`，不是直接调用 `MemoryService.write()`；因此覆盖 staging → capability `/write` → capability `/detail` → 权威 `detail get` → sidecar detail cache → staging 清理。
- **批次：** 1k `--batch-size 50`；2k/10k `--batch-size 100`（sidecar/capability 上限 100）。
- **读取采样：** 按 `index % 100` 的 detail-kind 桶分层；1k/2k 采 100 个，10k 采 200 个。查询文本为唯一 marker（含 4 位数字片段，触发 recall 的 exact/expand 意图）。
- **存储断言：** 写入后按 index 0/80/90/96 取 4 个探针，先经 capability `/query` 找到对应 MemoryRecord，再用 capability `/detail op=list` + `recordIds` 读取，断言 `detailKind` 分别为 `raw_chunk`（两类 conversation）、`tool_output`、`document_slice`。
- **计数审计（本轮新增）：** seed 响应中的每个 record ID 都进入内存集合；seed 后经 capability `/query` 分页读取所有非保留域（`includeHistory=true`、`includeArchived=true`），验证：
  1. 写入响应 ID 数量/去重数量等于请求 records；
  2. 每个种子 ID 在图中存在，且带 `scale-bench` tag；
  3. 所有非种子 MemoryRecord 单独按 domain/type/kind/tags/provenance 分组输出，检测其正文是否与种子重复；
  4. `status.counts.details` 必须精确等于请求 details。
  审计不是把 `memoryRecords >= records` 当通过；`--allow-extra-records` 仅用于生成完整诊断 JSON，若 extras 与种子正文重复，最终 status 仍强制为 `failed`。
- **规模化保护：** 默认 `--max-records 2000`、`--max-queries 500`；超过默认值必须显式 `--allow-large`，硬上限 100,000 records / 2,000 queries。整体默认超时 30 分钟，单请求默认 120 秒；启动前做磁盘/可用内存预检。
- **延迟定义：** 每次 await 的端到端墙钟时间；分位数为 nearest-rank（`ceil(p*n)-1`）。写入吞吐 = 逻辑 records / 总写入墙钟时间，不是单条并发吞吐。
- **RSS：** 宿主进程用 `process.memoryUsage().rss`；sidecar 用 `ps -o rss=` 读取子进程 RSS（KB → bytes）。
- **磁盘：** 逻辑字节为递归 `stat`，另有 `du -sk` 的分配字节。

## 5. 计数审计修复与 1k/2k 验证

### 5.1 为什么不能直接用 `memoryRecords === records` 作为唯一断言

旧脚本只比较 capability `/status` 的全局 `counts.memoryRecords` 与请求 records。这个计数包含所有非保留域的普通 MemoryRecord，但无法区分：

- 来自别的 domain/历史/非种子节点的记录；
- 产品路径重复写出的同正文记录；
- 一个批次部分提交后在重试中再次提交的尾部记录。

因此本轮把断言拆成两层：

1. **种子完整性：** 10,000 个写入响应 ID 是否全部、唯一、带 tag 地存在；
2. **额外记录透明化：** 任何非种子记录都进入 `countAudit.extras`，按 domain/type/kind/tags/provenance 分组；若正文与种子重复，直接判定产品重复写入并非通过。

| 机器可读证据 | `0.3.2-scale-benchmark-10k-failure-7386495.json` |

### 6.2 根因链

1. **sidecar 对 capability 的默认超时是 5s，且 mutating 请求会重试。**
   `packages/memory-runtime/src/sidecar/config.ts` 的默认 `capability.timeoutMs=5000`；`CapabilityClient.call()` 在 timeout/retryable 错误时使用**同一个请求体、同一个 `Idempotency-Key`** 重试（默认 `retries=2`，最多 3 次）。
2. **10k 的写入路径在高位已经明显超过单次 5s 预算。**
   原始 10k 的 batch 89–100 达到 103–160 s/批；写入链路含 capability 全图去重索引、逐条 `writeRecords`、tag/metadata 更新、detail 批次与权威回读。高负载下单个能力请求超过 5s 后，sidecar 会启动重试，而原请求仍在服务端继续执行。
3. **capability 幂等层没有 in-flight 去重/租约。**
   `withIdempotency()` 只在请求开始读 ledger、请求结束写 ledger；同一 composite key 的两个并发请求都可能看到 “不存在”，然后各自执行。受控探针用两个并发 `/write`（同一 key、同一 100 个 item）得到两个 `created=100, replayed=false`，图内 **200 records**。
4. **重试在中间快照上重建去重索引，原请求的尾部继续落图。**
   `handleWrite()` 在每个请求开始时 `buildDedupeIndex()` 全量扫描；重试看到的只是原请求当时的中间状态。重试创建了原请求尚未写入的尾部 item；原请求随后又写了一遍这些 item。seed 响应返回重试的 100 个 ID，原请求尾部成为 **非种子重复记录**。
5. **details 精确保持 10,000 的原因。**
   Detail 写入使用 seed 响应返回的 record ID 关联；重复的原请求尾部没有进入响应集合，因此没有额外 Detail。于是出现 10k 特有的 **records 多、details 正好相等** 签名。

## 7. 失败 / 中断路径证据

`tests/integration/scale-bench/failure-injection.mjs` 在最终 SHA `19cac09` 上重跑，6 个场景全部通过；使用同一真实 cluster，仅控制失败时机。

| 场景 | 退出码 | 结果 | 关键证据 | 清理 |
|---|---:|---|---|---|
| seed 注入失败 | 1 | `failed` | 写入 5 条 / 1 批次后抛错；5 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| read 注入失败 | 1 | `failed` | seed 完成 20/20；reads 完成 1 个样本后抛错；14 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| SIGTERM 中断 | 143 | `interrupted` | 已完成 20 条 / 2 批次；8 次 checkpoint；partial JSON 保留 | `cleaned=true`，`residualPids=[]` |
| SIGINT 中断 | 130 | `interrupted` | 已完成 20 条 / 2 批次；8 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| sidecar SIGKILL | 0（重启后跑完） | `passed` | kill 于第 1 批次，pid `84445`；重启 pid `84460` 被 tracker 记录；最终 20/20、reads 2/2 | `cleaned=true`，`residualPids=[]` |
| 冻结 sidecar + 清理升级 | 1 | `failed` | `sidecar_sigstop` 冻结；清理 SIGTERM 5s 未退出后 SIGKILL；`escalation=SIGKILL` | `cleaned=true`，`tempHomeRemoved=true`，`residualPids=[]` |

实现要点：

- **partial JSON：** 每批次、每 5 个 read 样本、进入失败/中断、cleanup 前后都会原子写入 `<output>.tmp-* → rename`；最终 JSON 也走同一路径。
- **SIGINT/SIGTERM：** 第一次信号请求停止，循环在安全点抛 `AbortError` 并写 partial JSON；20 秒内未完成则 emergency sync 落盘并 SIGKILL tracked sidecar，退出码 130/143。
- **超时：** 整体 `--timeout-ms`（默认 30 分钟）按同一停止路径处理，退出码 124；单请求 `--request-timeout-ms` 默认 120 秒。
- **SIGKILL fallback：** 清理先停 tracked sidecar；SIGTERM 5 秒未退出则 SIGKILL，再由 `ps -axo` 扫描 `--parent-pid <本进程>` 的残留并复检。
- **tempHomeRemoved：** 清理后真实 `stat` 检查路径，存在则重试 `rm` 并暴露非 ENOENT 错误。
- **PID 跟踪：** `cluster-start`、每个 checkpoint、故障注入前都会刷新 discovery pid；tracker 保留历史 PID 和事件，重启后的新 PID 会被记录并在 cleanup 中逐一停止。

## 10. 限制与风险

1. **10k 通过只代表本机单次 run。** 最终 10k 在 `c37e74b` 上通过，但宿主不是空闲独立机；绝对吞吐、p95/p99 与 RSS 只代表当时环境，不是 SLA 或跨平台承诺。原始 `7386495` 的 10,023/10,000 失败仍作为历史证据保留。
2. **10k 读取是分层 marker 样本，不是质量结论。** 200/200 样本完成、coverage 100%，但查询文本是唯一合成 marker；`recall@k`、遗漏率、误召回轮次率仍需独立质量基准。
3. **本机不是空闲独立机。** 1k/2k/探针与最终 10k 运行时都存在其它 Hermes/系统负载，第二轮 10k 还曾遇到 load average 约 19；绝对性能只代表当时环境。
4. **不是宿主/模型证据。** 没有真实 DSH/Hermes/OpenCode/OpenChamber 进程、真实模型、P2P 对端或 Console UI；不能用于 C19 的宿主注入、模型 canary 或跨设备同步开销声明。
5. **查询是合成 marker。** 每条查询都精确包含唯一 marker，命中率高不代表自然语言召回质量。
6. **分位数样本有限。** 1k/2k 各 100 个读取样本，10k 为 200 个；p99 实际接近 max，nearest-rank 分位数较粗，报告同时给出 max。
7. **Detail 覆盖是分层样本结论。** 1k/2k/10k 的样本覆盖均为 100%，10k 为 200 个分层样本（四个 detail-kind），不是对 10,000 条逐条展开。
8. **缓存与账本只验证到 10k。** 10k 的 detail cache 达到 5,000 条上限 / 6.42 MB，幂等账本 200 条 / 5.93 MB；超过 10k 的增长、淘汰与 256 MiB 字节上限未验证。
9. **构建绑定证明的是元数据一致，不是可复现构建。** `version.json` 的 sha 与 HEAD 一致、dist 文件哈希已记录；同一 SHA 重新构建的字节级可复现性未验证。
