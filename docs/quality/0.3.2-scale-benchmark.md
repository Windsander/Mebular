## 3. 数据集与工作负载

- **数据形状：** 每个逻辑项 = 1 个 raw chunk + 1 个 host candidate → 1 条 MemoryRecord + 1 条 Detail。
- **detail-kind 分布（按索引模 100 固定）：**
  - 80% `user` / `raw_chunk`（conversation）
  - 10% `assistant` / `raw_chunk`（conversation）
  - 6% `tool` / `tool_output`
  - 4% `user` / `document_slice`
- **内容：** 合成 marker + 固定说明文本，约 220–260 bytes/条；无真实用户内容、token、密钥或真实 home 路径。
- **写入路径：** 通过真实 sidecar `POST /ingest`，不是直接调用 `MemoryService.write()`；因此覆盖 staging → capability `/write` → capability `/detail` → 权威 `detail get` → sidecar detail cache → staging 清理。
- **批次：** 1k smoke `--batch-size 50`；10k full 建议 `--batch-size 100`（sidecar/capability 上限 100）。
- **读取采样：** 按 `index % 100` 的 detail-kind 桶分层，使每类 detail-kind 都进入样本；1k 采 100 个、10k 采 200 个。查询文本为唯一 marker（含 4 位数字片段，触发 recall 的 exact/expand 意图）。
- **存储断言：** 写入后按 index 0/80/90/96 取 4 个探针，先经 capability `/query` 找到对应 MemoryRecord，再用 capability `/detail op=list` + `recordIds` 读取，断言 `detailKind` 分别为 `raw_chunk`（两类 conversation）、`tool_output`、`document_slice`。
- **规模化保护：** 默认 `--max-records 2000`、`--max-queries 500`；超过默认值必须显式 `--allow-large`，硬上限 100,000 records / 2,000 queries。整体默认超时 30 分钟，单请求默认 120 秒；启动前做磁盘/可用内存预检。
- **延迟定义：** 每次 await 的端到端墙钟时间；分位数为 nearest-rank（`ceil(p*n)-1`）。写入吞吐 = 逻辑 records / 总写入墙钟时间，不是单条并发吞吐。
- **RSS：** 宿主进程用 `process.memoryUsage().rss`；sidecar 用 `ps -o rss=` 读取子进程 RSS（KB → bytes）。
- **磁盘：** 逻辑字节为递归 `stat`，另有 `du -sk` 的分配字节。

## 6. 失败 / 中断路径证据

`tests/integration/scale-bench/failure-injection.mjs` 使用同一真实 cluster，仅控制失败时机；所有 6 个场景都要求 partial JSON 可读、状态字段正确、临时 home 删除、sidecar 停止且无残留 PID。

| 场景 | 退出码 | 结果 | 关键证据 | 清理 |
|---|---:|---|---|---|
| seed 注入失败 | 1 | `failed` | 写入 5 条 / 1 批次后抛错；`seed.faultInjection.type=seed_fail_after_batches`；5 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| read 注入失败 | 1 | `failed` | seed 完成 20/20；reads 完成 1 个样本后抛错；`reads.faultInjection.type=reads_fail_after_samples`；13 次 checkpoint | `cleaned=true`，`residualPids=[]` |
| SIGTERM 中断 | 143 | `interrupted` | 已完成 20 条 / 2 批次；`abort.reason=SIGTERM`；8 次 checkpoint；partial JSON 保留已完成进度 | `cleaned=true`，`residualPids=[]` |
| SIGINT 中断 | 130 | `interrupted` | 已完成 20 条 / 2 批次；`abort.reason=SIGINT`；8 次 checkpoint；与 SIGTERM 共用停止/清理路径 | `cleaned=true`，`residualPids=[]` |
| sidecar SIGKILL | 0（重启后跑完） | `passed` | kill 于第 1 批次，pid `68648`；重启 pid `68660` 被 tracker 记录；最终 20/20、reads 2/2 | `cleaned=true`，`residualPids=[]` |
| 冻结 sidecar + 清理升级 | 1 | `failed` | `sidecar_sigstop` 冻结 pid `68719`；清理先 SIGTERM，5s 未退出后 SIGKILL；`sidecarStop[0].escalation=SIGKILL` | `tempHomeRemoved=true`，`residualPids=[]` |

实现要点：

- **partial JSON：** 每批次、每 5 个 read 样本、进入失败/中断、cleanup 前后都会原子写入 `<output>.tmp-* → rename`；最终 JSON 也走同一路径。
- **SIGINT/SIGTERM：** 第一次信号请求停止，循环在安全点抛 `AbortError` 并写 partial JSON；20 秒内未完成则 emergency sync 落盘并 SIGKILL tracked sidecar，退出码 130/143。
- **超时：** 整体 `--timeout-ms`（默认 30 分钟）按同一停止路径处理，退出码 124；单请求 `--request-timeout-ms` 默认 120 秒。
- **SIGKILL fallback：** 清理先停 tracked sidecar；SIGTERM 5 秒未退出则 SIGKILL，再由 `ps -axo` 扫描 `--parent-pid <本进程>` 的残留并复检。
- **tempHomeRemoved：** 不再信任 cluster 内部的 `rm().catch()`；清理后真实 `stat` 检查路径，存在则重试 `rm` 并暴露非 ENOENT 错误。
- **PID 跟踪：** `cluster-start`、每个 checkpoint、故障注入前都会刷新 discovery pid；tracker 保留历史 PID 和事件，重启后的新 PID 会被记录并在 cleanup 中逐一停止。

## 7. 发现与建议

### 7.1 写入吞吐与单条成本

- 1k 的端到端 ingest p50 约 4.9 s/50 条，折合 98–99 ms/条；写入吞吐 9.8–9.9 条/s。
- 这条链路包含：sidecar 串行 ingest 锁、staging 写入与校验、capability `/write` 逐条图写入、capability `/detail` 批量写入、**每条 Detail 的权威回读**、detail cache 写入、staging 清理、幂等响应账本持久化。
- 因此该数字是“真实用户路径吞吐”，不是纯 GraphStore 写入吞吐。若需要定位到单组件，建议 WP6 后续增加 capability `/write` 与 `/detail` 的独立微基准；本会话不修改产品代码。
- 风险：10k 全量在本机外推约 **3–4 小时**（旧 harness 跑到 2k/10k 已约 8–9 分钟，且成本随规模上升），不是 18–25 分钟；不适合接入普通 PR CI。应作为手动/nightly 规模门禁，或降低到 1k smoke 作 PR 证据、10k 作发布前证据。

### 7.2 Detail 展开覆盖缺口（P1，已交 WP3）

**现象：** 图内 1,000 条 Detail 全部存在（`counts.details=1000`），存储侧 4 个探针也确认 `tool_output`/`document_slice` 的 kind 正确；但召回读取样本中 `tool_output` 与 `document_slice` 的碎片没有 `detailIds`，导致 `/recall/:id/expand` 无法发起；conversation 两类均 100% 可展开。

**根因：** `packages/memory-runtime/src/sidecar/recall.ts` 的 `resolveDetailIds()` 在记录没有前向 `detailIds` 时，向 capability `/detail op=list` 传入固定 `detailKinds: ['raw_chunk']`。而 WP1 已把 `tool_output`、`document_slice` 作为合法 DetailKind 写入；capability 也不会在 MemoryRecord 上保留前向 `provenance.detailIds`（契约 §2.3）。于是 recall 只找到 raw_chunk，非 raw_chunk 的详情永远不会被关联到召回碎片。

**影响：**

- 召回碎片会出现 `hasDetail=true` 但 `detailIds=[]`、`detailAvailable=false`、`detailAvailability=['pending_sync']`；`/expand` 只能返回 `detail=null` + `detail_pending_sync`，把“未关联”误报成“同步中”，用户无法看到工具输出/文档切片原文。
- 不影响图内 Detail 数量、存储 kind 和 retention 元数据；不影响 conversation 路径。
- 这属于 WP1 数据路径/C03 详情证据关联的验收 blocker，不应以“规模基准通过”掩盖。产品修复已交 WP3；本基准不改产品代码。

**建议（不修改产品，仅建议）：**

1. `resolveDetailIds()` 查询 canonical detail kind 集合（`raw_chunk`、`message`、`tool_output`、`document_slice`），或省略 `detailKinds` 过滤，由 capability 做域/记录/保留校验；保持最多 3 条和现有配额。
2. 增加回归测试：分别写入 conversation、tool_output、document_slice 各一条 Detail，召回后断言 `detailIds` 非空且 `/expand` 返回对应原文。
3. 修复后重跑本基准的 1k/10k，确认 `detailExpandCoverage.coverageRate` 从 90% 提升到 100%，且 `tool_output`/`document_slice` 分项为 100%。

### 7.3 磁盘、缓存与账本

- `device.jsonl` 在 1k 时约 16.19 MB，约 **16 KB/条记录+详情**；事件日志保留完整 create/update 节点版本是契约已披露行为，不是泄漏，但 10k 时需要关注磁盘增长。
- detail cache 在 1k 时为 1,000 条 / 1.28 MB；10k 写入 10,000 条 Detail，预计会触及 **5,000 条 / 256 MiB** 上限，最终条目数需以 10k JSON 的 `detailCacheEntries` 为准，不能把 1k 的 1,000 条线性外推。
- 幂等账本在 1k/20 个 ingest 批次后为 **40 条 / 0.60 MB**（每个批次 2 条：`/write` 与 `/detail` 响应）。10k 用 batch-size 100 时为 100 个批次，预期约 **200 条**，远低于 5,000 条上限，**不会触及账本上限**；不要用记录数推断账本条数。10k 仍以 JSON 的 `idempotencyLedgerEntries` 为准。
- 1k 后 sidecar RSS 增加约 77–80 MB、宿主 RSS 增加约 28–89 MB（宿主数值受 V8 GC 影响明显）；这是含 Node/V8 堆、图索引和缓存的总量，不是纯数据大小。10k 数值需未来长跑确认。

## 8. 10k full 尝试结果（未完成，不计为通过）

**结论：** 在本机（Intel i7-8850H / 32 GiB / Node 26 / 旧 harness SHA）无法在合理时间内完成 10k full。运行到 **2,000/10,000** 时已耗时约 **8–9 分钟**，据此中止；未生成 `docs/quality/0.3.2-scale-benchmark-10k.json`，也不以 1k 数据外推填充 10k 表格。最终 harness（`1626dd5`）尚未重跑 10k。

| 中止时观测项 | 值 |
|---|---:|
| 已完成记录 / 详情 | 2,000 / 2,000（20/100 批次） |
| 已耗时 | 约 8–9 分钟 |
| 折算吞吐 | 约 3.7–4.1 records/s |
| 宿主进程 RSS | 183.2 MB |
| sidecar RSS | 172.7 MB |
| 临时 home 磁盘 | 57 MB（`du -sh`） |
| `device.jsonl` | 42 MB / 32,400 行 |
| 幂等账本 | 1.5 MB |

**为什么判定不合理：** 1k 时写入成本约 0.10 s/条；2k 时约 0.25–0.27 s/条，成本随数据量明显上升。即使按线性增长保守外推，10k 也需约 3–4 小时；若继续增长则更久。这不是“等一会儿就好”的噪声，而是需要在性能修复后复测的规模问题。

**后续运行要求：**

1. 先定位写入路径的数据规模依赖。代码审查给出的优先怀疑点（尚未通过固定 batch 阶梯证实）：capability `buildDedupeIndex()` 每批全量扫描节点；`MemoryService.writeDetailsLocked()` 每批 `detailNodes()` 全量扫描；`ensureDetailQuota()` 对 `live` 数组逐项做 O(n) 域/云用量计算；以及事件日志每个逻辑对象追加多条含完整节点版本的记录（100 条记录+详情产生 1,200 行 / 1.5 MB，约 15 KB/逻辑项）。先做固定 batch 的 1k/2k/4k 阶梯和 capability `/write`、`/detail` 分项计时，再决定修复或接受长跑。
2. 修复后在**干净 SHA** 上运行 §9 的 10k 命令，保存 `docs/quality/0.3.2-scale-benchmark-10k.json`。
3. 若最终决定不修复，由 chief/用户显式接受“10k 规模证据缺失”，并把 C19 的规模声明收窄；不得用 1k 结果替代。

## 10. 限制与风险

1. **不是宿主/模型证据。** 没有真实 DSH/Hermes/OpenCode/OpenChamber 进程、真实模型、P2P 对端或 Console UI；不能用于 C19 的宿主注入、模型 canary、Recall@k 质量或升级/回滚声明。
2. **查询是合成 marker。** 每条查询都精确包含唯一 marker，命中率高不代表自然语言召回质量；`recall@k`、遗漏率、误召回轮次率需由质量基准单独测量。
3. **单机单次。** 绝对值依赖 Intel i7-8850H、Node 26、macOS 和当时负载；不应把 p95 当作跨平台 SLA。1k 两次写入墙钟差异约 1%，p50/p95 接近；读取 p50 较稳定，尾部延迟仍有明显波动。
4. **小样本分位数。** 1k/100 样本、10k/200 样本的 p99 实际接近 max，nearest-rank 分位数较粗；报告同时给出 max。
5. **10k 运行成本高且本机未完成。** 旧 harness 在 2k/10k 已耗时约 8–9 分钟，外推 3–4 小时；期间生成数十至百 MB 级临时图/事件日志。已中止并清理，未把 2k 观测写成 10k 结果。不要在用户真实 home 或共享 CI runner 上无约束运行。
6. **已存在的 P1 详情覆盖缺口。** 见 §7.2；修复前不应宣称“所有 detail-kind 均可展开”。存储侧已证明 Detail 存在，缺口在 recall 关联。本会话按授权不修改产品代码。
7. **缓存与账本上限尚未在 10k 验证。** 1k 未触及 detail cache 的 5,000 条上限；10k 预计会触及。幂等账本在 10k batch-size 100 下预计约 200 条，不会触及 5,000 条上限。最终以未来 10k JSON 的 `detailCacheEntries`、`idempotencyLedgerEntries` 为准。
8. **构建绑定证明的是元数据一致，不是可复现构建。** `version.json` 的 `sha` 与 HEAD 一致、dist 文件哈希已记录；同一 SHA 重新构建的字节级可复现性未验证。
