## 4. 真实 E2E：decision → outcome 闭环

脚本：`tests/integration/host-e2e/opencode-intervention-outcome.mjs`
（等价命令：`npm run verify:opencode:intervention`）。

真实部分：`opencode serve/run` v2.4.1、`@mebular/opencode-plugin` 由 OpenCode 按
`opencode.json` 加载、真实 sidecar discovery/host token、真实 `/context` `/traces`
`/recall/:id/outcome` `/intervention/reset`、真实 MCP capability 与 GraphStore。
fake 部分：OpenAI-compatible provider 只负责返回固定文本，让真实宿主完成 turn；没有

## 5. 性能

`packages/memory-runtime/tests/sidecar/acceptance-performance.test.ts` +
`intervention-performance.test.ts`，fake capability 但真实本地 HTTP 往返：

| heuristic p95 额外开销 | **中位数 0.30 ms**（3 轮：0.30 / −12.93 / 3.21 ms） |

0.30 ms，低于计划中的 5 ms 目标（CI 噪声下测试断言 <10 ms）。

## 8. 已知限制

1. **0.4.0 未发布。** 默认 `off`；`model` 与按域自适应阈值是 experimental，发布前仍需
   canary / Go-No-Go。
2. **真实模型 smoke 未跑。** 本机无本地模型；E2E 的宿主只使用 fake OpenAI-compatible
   provider，模型 planner 由 `intervention-model*.test.ts` 的 fake gateway 覆盖。因此
   本报告不证明真实模型延迟、质量或 prompt 安全在真实模型上的表现。
3. **E2E 不验证答案质量。** 它验证 decision/outcome 的真实 HTTP 闭环，不评估模型回答是否
   更好；答案质量评估仍需 golden set + judge。
4. **Console 截图是 fixture 证据。** 截图来自 `verify:console:ui` 的 fake sidecar 数据，
   用于 UI 状态；真实 sidecar 的 trace 字段由 §4 单独断言。
5. **归因启发式有噪声。** `reasked/corrected/too_*` 由插件正则和上一轮 decision 推断，
   本报告只证明它按设计触发并落库，不证明长期策略效果。
6. **仅 OpenCode 宿主。** DSH / Hermes 复用同一 outcome API，但 0.4.0 未接；跨设备策略
   同步不在范围内。
7. **性能数字是单机样本。** 非空闲开发机，125 s 全量 suite 中有 IO 抖动；性能只作为
   回归证据，不是 SLA。

## 9. 生产问题（已修复）

0.4.0 E2E 中发现、自 0.3.0 起存在的去重契约不一致，已在 `feat/0.4-dedup-fix`
修复（commit `2c21325`，基于 `feat/0.4-integration@c82969d`）。

- **问题。** OpenCode 插件在 `rememberInjected()` 中把 `/context` 响应的 **fragment
  ID**（`mf_…`）放进 `alreadyInjectedIds`；sidecar 的 `buildCandidates()` 只拿它与
  片段的 **source/record ID**（`sourceIds`）比较，`intervention.ts` 的 `noveltyOf()`
  也只比较 `candidate.sourceIds`。结果是宿主级“已注入”去重/novelty 可能不生效，
  重复 turn 仍会重新召回同一记录（除非其他策略原因造成 silent）。
- **根因。** fragment ID 按 0.3 契约是“本次召回的临时 ID”、每次召回重新生成，因此
  只做字面比较永远无法命中上一轮回传的 `mf_…`。
- **修复。**
  - `buildCandidates()`：`alreadyInjectedIds` 同时匹配 `sourceIds` 与 `fragment.id`；
    另用进程内有界别名表（`fragment ID → source IDs`，最多 4096 条、FIFO 淘汰）
    把宿主回传的旧 `mf_…` 解析为源记录 ID，保证真实插件回传的 fragment ID 能命中。
  - `intervention.ts` 的 `noveltyOf()`：同时检查 `candidate.fragmentId` 与
    `candidate.sourceIds`，任一命中即 `novelty=0`。
  - 兼容性：source/record ID 仍直接有效；未知 ID 不影响召回；`alreadyInjectedIds`
    的 100 条上限与校验不变；quarantine 优先级不变。
  - 插件/Console 生产代码未改（插件已经传 fragment ID）。
- **测试证据**（commit `2c21325`）：
  - `packages/memory-runtime/tests/sidecar/recall.test.ts`：fragment ID 去重（第二次
    `/context` 返回空 fragments/blocks、`silenceReason=already_injected`、trace
    `filteredReason=already_injected`）；source ID 仍然生效；无关 ID 不影响召回。
  - `packages/memory-runtime/tests/sidecar/intervention.test.ts`：fragment ID →
    `no_novelty` / `scores.novelty=0`；source ID 路径保持；无关 fragment/source ID →
    `novelty=1` 且正常 `speak`。
  - `node --experimental-vm-modules node_modules/jest/bin/jest.js packages/memory-runtime/tests --runInBand`
    → 42 suites / 465 tests 全绿（含 off/shadow/heuristic 回归）。
  - `node --experimental-vm-modules node_modules/jest/bin/jest.js tests/opencode-plugin --runInBand`
    → 3 suites / 140 tests 全绿（插件契约未变）。
