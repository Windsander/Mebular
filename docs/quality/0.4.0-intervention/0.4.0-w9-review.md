## 2. 根因与修复

原 harness 只用 `serve` stdout 里的 `server listening on ...` 作为就绪条件，并在其后立即发起第一轮 `opencode run`。监听日志出现不等于 CLI 客户端路径已经可完成请求，于是首轮偶发传输层失败。

修复（`opencode-intervention-outcome.mjs`）：

1. **真实 health 等待**
   - 新增 `waitForServerHealth()`：用与 `opencode run --server` 相同的 CLI 客户端执行
     `opencode api GET /api/info --server <url>`，要求退出 0 且返回含 `version` 的 V2 JSON。
   - 上限 30s、250ms 间隔；探测次数/耗时写入日志。
   - `真实 opencode serve 启动` 断言现在要求 **listening + health 同时成立**（仍是 1 个断言）。
2. **有界 warmup**
   - server health 后先跑一次真实
     `opencode run --archived --server <url> --format json hi`。
   - 默认上限 3 次（`MEBULAR_OUTCOME_WARMUP_ATTEMPTS` 可覆盖，`0` 为跳过），每次 120s 超时；
     每轮记录 attempt/耗时/sessionID。
   - warmup 本身**不是断言**，不改变 47 项契约；仅吸收启动抖动。非传输类失败立即停止重试并写日志。
3. **首轮有界真实重试**
   - `turn()` 只对传输层症状（`Could not reach server`、`ECONNREFUSED`、
     `ECONNRESET`、`socket hang up`、`fetch failed` 等）重试；
   - 首轮最多 3 次、已建会话的后续轮最多 2 次，逐次记录重试原因；
   - 非传输类失败不重试，最终仍由原有 `check` 判定；**没有吞掉真实断言失败，也没有减少断言**。
